# M2 시나리오 상세 작업지시서

## 0. 결정 필요 사항 및 기본 처리

아래 항목은 구현 편차를 줄이기 위해 기본값을 정한다. 사용자 또는 PM이 별도 지시하면 해당 지시를 우선한다.

| # | 항목 | 기본 처리 | 구현 영향 |
|---|---|---|---|
| 1 | OPERATOR 계정 시딩 | 운영 기본 OPERATOR 계정은 비활성 상태로 생성하고 `must_change_password=true`로 둔다. 초기 로그인/활성화 흐름에서 비밀번호 변경을 강제한다. | 기본 계정 즉시 권한 행사를 차단하고 임시 비밀번호 사용을 방지 |
| 2 | 관리자 경로 권한 | `/admin/**`은 `ADMIN`, `OPERATOR` 모두 허용한다. 관리자 메뉴는 Thymeleaf Security 권한 조건으로 분기한다. | OPERATOR가 시나리오 관리 진입 가능 |
| 3 | REST CSRF/인증 실패 | `CookieCsrfTokenRepository.withHttpOnlyFalse()` 적용, `/admin/api/**` 인증 실패/권한 실패는 JSON으로 반환한다. | AJAX 오류 처리 일관성 확보 |
| 4 | 감사 로그 detail | `AuditTrailRecorder`를 추가해 서비스에서 대상 ID와 before/after JSON을 직접 기록한다. 기존 `@Audited` AOP는 유지한다. | M2 감사 표준 수용 기준 충족 |
| 5 | 미리보기 범위 | M2에서는 서버 렌더 시뮬레이터로 한정한다. 옵션 클릭은 GET 파라미터로 다음 노드를 렌더링한다. | M3 챗봇 위젯 미구현에 따른 차단 제거 |
| 6 | 키워드/유사어 저장 동시성 | 단일 트랜잭션 안에서 기존 키워드/유사어 전체 삭제 후 재삽입한다. 낙관적 락은 M2 범위에서 제외한다. | 구현 단순화, 충돌 정책 명확화 |
| 7 | 게시 버전 재편집 | `PUBLISHED`, `ARCHIVED` 버전 직접 수정은 `STATE_CONFLICT`로 차단한다. 화면에는 "복제 후 새 초안" 버튼만 노출한다. | 게시 데이터 불변성 보장 |
| 8 | 신규 게시 시 기존 게시 버전 | 같은 시나리오의 직전 `PUBLISHED` 버전은 자동 `ARCHIVED`로 전환한다. | 시나리오당 게시 버전 1개 유지 |
| 9 | Flyway V3/V3.1 분리 | V3는 본 문서 1절 SQL 기준의 시나리오 baseline만 작성한다. `users.must_change_password`는 V3.1로 분리한다. | 구현자별 DDL 편차와 인증 테이블 변경 범위 혼선을 최소화 |
| 10 | 통합 테스트 컨테이너 | `@Container static PostgreSQLContainer<?>` 단일 컨테이너와 `@DynamicPropertySource`를 사용한다. | 테스트 부팅 비용 완화 |
| 11 | 쿠키 보안 속성 | 세션성 식별 쿠키는 `SameSite=Lax`, `Secure=true`, `HttpOnly=true`를 기본값으로 한다. | 운영 HTTPS 전제 쿠키 보안 기준 고정 |
| 12 | CSRF 쿠키 예외 | CSRF 토큰 쿠키는 `HttpOnly=false` 예외를 둔다. `Secure=true`, `SameSite=Lax`는 동일 적용한다. | AJAX CSRF 헤더 전송 가능 |
| 13 | 프록시 헤더 | `server.forward-headers-strategy=framework`를 사용하고 prod 프로파일에서만 부팅 경고 로그를 출력한다. | nginx HTTPS 종단과 dev/stage 로그 잡음 분리 |
| 14 | 매칭 캐시 TTL | M3 키워드/유사어 매칭 캐시 기본 TTL은 300초로 한다. | 캐시 무효화 훅 미구현 시에도 정합성 회복 |

## 1. Flyway V3 SQL

파일: `3.개발/cleverchat/src/main/resources/db/migration/V3__scenario_baseline.sql`

```sql
CREATE TABLE scenario_category (
    id BIGSERIAL PRIMARY KEY,
    parent_id BIGINT NULL,
    name VARCHAR(100) NOT NULL,
    sort_order INTEGER NOT NULL DEFAULT 0,
    enabled BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT fk_scenario_category_parent
        FOREIGN KEY (parent_id) REFERENCES scenario_category(id) ON DELETE SET NULL
);

CREATE UNIQUE INDEX ux_scenario_category_root_name
    ON scenario_category (name)
    WHERE parent_id IS NULL;

CREATE UNIQUE INDEX ux_scenario_category_parent_name
    ON scenario_category (parent_id, name)
    WHERE parent_id IS NOT NULL;

CREATE INDEX ix_scenario_category_parent_sort
    ON scenario_category (parent_id, sort_order, id);

CREATE TABLE scenario (
    id BIGSERIAL PRIMARY KEY,
    category_id BIGINT NOT NULL,
    title VARCHAR(150) NOT NULL,
    description TEXT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'DRAFT',
    active_version_id BIGINT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT fk_scenario_category
        FOREIGN KEY (category_id) REFERENCES scenario_category(id),
    CONSTRAINT ck_scenario_status
        CHECK (status IN ('DRAFT', 'ACTIVE', 'INACTIVE', 'DELETED'))
);

CREATE INDEX ix_scenario_category_status
    ON scenario (category_id, status, id DESC);

CREATE INDEX ix_scenario_title
    ON scenario (title);

CREATE TABLE scenario_version (
    id BIGSERIAL PRIMARY KEY,
    scenario_id BIGINT NOT NULL,
    version_no INTEGER NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'DRAFT',
    start_node_id BIGINT NULL,
    created_by VARCHAR(100) NOT NULL,
    published_at TIMESTAMPTZ NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT fk_scenario_version_scenario
        FOREIGN KEY (scenario_id) REFERENCES scenario(id) ON DELETE CASCADE,
    CONSTRAINT ux_scenario_version_no
        UNIQUE (scenario_id, version_no),
    CONSTRAINT ck_scenario_version_status
        CHECK (status IN ('DRAFT', 'PUBLISHED', 'ARCHIVED'))
);

CREATE UNIQUE INDEX ux_scenario_version_published_one
    ON scenario_version (scenario_id)
    WHERE status = 'PUBLISHED';

CREATE INDEX ix_scenario_version_scenario_status
    ON scenario_version (scenario_id, status, version_no DESC);

CREATE TABLE scenario_node (
    id BIGSERIAL PRIMARY KEY,
    version_id BIGINT NOT NULL,
    node_key VARCHAR(80) NOT NULL,
    node_type VARCHAR(20) NOT NULL,
    title VARCHAR(150) NOT NULL,
    content TEXT NULL,
    sort_order INTEGER NOT NULL DEFAULT 0,
    metadata JSONB NOT NULL DEFAULT '{}'::jsonb,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT fk_scenario_node_version
        FOREIGN KEY (version_id) REFERENCES scenario_version(id) ON DELETE CASCADE,
    CONSTRAINT ux_scenario_node_key
        UNIQUE (version_id, node_key),
    CONSTRAINT ck_scenario_node_type
        CHECK (node_type IN ('QUESTION', 'ANSWER', 'BRANCH', 'END'))
);

CREATE INDEX ix_scenario_node_version_sort
    ON scenario_node (version_id, sort_order, id);

CREATE TABLE scenario_node_option (
    id BIGSERIAL PRIMARY KEY,
    node_id BIGINT NOT NULL,
    next_node_id BIGINT NULL,
    label VARCHAR(150) NOT NULL,
    condition_expr VARCHAR(500) NULL,
    sort_order INTEGER NOT NULL DEFAULT 0,
    enabled BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT fk_scenario_node_option_node
        FOREIGN KEY (node_id) REFERENCES scenario_node(id) ON DELETE CASCADE,
    CONSTRAINT fk_scenario_node_option_next
        FOREIGN KEY (next_node_id) REFERENCES scenario_node(id) ON DELETE SET NULL
);

CREATE INDEX ix_scenario_node_option_node_sort
    ON scenario_node_option (node_id, sort_order, id);

CREATE INDEX ix_scenario_node_option_next
    ON scenario_node_option (next_node_id);

CREATE TABLE scenario_keyword (
    id BIGSERIAL PRIMARY KEY,
    scenario_id BIGINT NOT NULL,
    keyword VARCHAR(100) NOT NULL,
    weight INTEGER NOT NULL DEFAULT 100,
    enabled BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT fk_scenario_keyword_scenario
        FOREIGN KEY (scenario_id) REFERENCES scenario(id) ON DELETE CASCADE,
    CONSTRAINT ux_scenario_keyword
        UNIQUE (scenario_id, keyword),
    CONSTRAINT ck_scenario_keyword_weight
        CHECK (weight BETWEEN 0 AND 100)
);

CREATE INDEX ix_scenario_keyword_scenario_enabled
    ON scenario_keyword (scenario_id, enabled, weight DESC);

CREATE TABLE scenario_synonym (
    id BIGSERIAL PRIMARY KEY,
    keyword_id BIGINT NOT NULL,
    synonym VARCHAR(100) NOT NULL,
    weight INTEGER NOT NULL DEFAULT 100,
    enabled BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT fk_scenario_synonym_keyword
        FOREIGN KEY (keyword_id) REFERENCES scenario_keyword(id) ON DELETE CASCADE,
    CONSTRAINT ux_scenario_synonym
        UNIQUE (keyword_id, synonym),
    CONSTRAINT ck_scenario_synonym_weight
        CHECK (weight BETWEEN 0 AND 100)
);

CREATE INDEX ix_scenario_synonym_keyword_enabled
    ON scenario_synonym (keyword_id, enabled, weight DESC);

ALTER TABLE scenario
    ADD CONSTRAINT fk_scenario_active_version
    FOREIGN KEY (active_version_id) REFERENCES scenario_version(id) ON DELETE SET NULL;

ALTER TABLE scenario_version
    ADD CONSTRAINT fk_scenario_version_start_node
    FOREIGN KEY (start_node_id) REFERENCES scenario_node(id) ON DELETE SET NULL;
```

주의:

- `scenario_node_option.next_node_id`가 같은 `version_id`의 노드인지 여부는 서비스에서 검증한다.
- `scenario.active_version_id`가 같은 `scenario_id`의 `PUBLISHED` 버전인지 여부도 서비스에서 검증한다.
- `updated_at` 자동 갱신 트리거는 M2 범위에서 필수로 두지 않는다. 수정 SQL에서 명시 갱신한다.
- V3에는 `users` 테이블 변경을 포함하지 않는다.

## 1.1 Flyway V3.1 SQL

파일: `3.개발/cleverchat/src/main/resources/db/migration/V3_1__auth_must_change_password.sql`

```sql
ALTER TABLE users
    ADD COLUMN must_change_password BOOLEAN NOT NULL DEFAULT false;
```

주의:

- 기존 ADMIN 계정은 기본값 `false`로 유지한다.
- OPERATOR 시더는 V3.1 적용 후 비활성 계정(`enabled=false`)과 `must_change_password=true` 기본값으로 생성한다.
- V3.1은 인증 테이블 보완만 담당하고 M2 시나리오 테이블을 수정하지 않는다.

## 3. 도메인 검증 규칙

### 3.1 공통 입력 검증

| 대상 | 규칙 |
|---|---|
| 카테고리명 | 필수, 1~100자, 같은 부모 하위 중복 불가 |
| 시나리오 제목 | 필수, 1~150자 |
| 설명 | 선택, 최대 2,000자 |
| 노드 키 | 필수, 영문/숫자/하이픈/언더스코어, 1~80자 |
| 노드 제목 | 필수, 1~150자 |
| 노드 본문 | 선택, 최대 10,000자 |
| 옵션 라벨 | 필수, 1~150자 |
| 조건식 | 선택, 최대 500자. M2에서는 실행하지 않고 저장만 한다. |
| 키워드/유사어 | 필수, 1~100자, 앞뒤 공백 제거 후 저장 |
| 가중치 | 0~100 정수 |

### 3.2 그래프 무결성

- 버전 저장 대상은 반드시 해당 시나리오의 `DRAFT` 버전이어야 한다.
- 요청의 `startNodeKey`는 `nodes` 안에 존재해야 한다.
- `nodeKey`는 버전 안에서 중복될 수 없다.
- 옵션의 `nextNodeKey`는 같은 요청의 `nodes` 안에 존재해야 한다. 단, `END`로 종료하는 선택지가 필요하면 `nextNodeKey`를 생략할 수 있다.
- `END` 노드는 옵션을 가질 수 없다.
- `QUESTION`, `BRANCH` 노드는 최소 1개 이상의 옵션을 권장한다. M2에서는 오류가 아니라 경고 수준으로 응답 detail에 포함할 수 있다.
- 순환 그래프는 허용한다. 단, 시작 노드에서 도달 불가능한 노드는 게시 시 `VALIDATION_ERROR`로 차단한다.
- DB 저장은 `scenario_node_option` 삭제, `scenario_node` 삭제, 노드 재삽입, 옵션 재삽입 순서로 처리한다.

### 3.3 상태 전이

| 명령 | 허용 상태 | 결과 | 실패 코드 |
|---|---|---|---|
| 시나리오 수정 | `DRAFT`, `INACTIVE` | 기본정보 수정 | `STATE_CONFLICT` |
| 시나리오 삭제 | `DRAFT`, `INACTIVE` | `DELETED` | `STATE_CONFLICT` |
| 새 초안 버전 생성 | `DRAFT`, `ACTIVE`, `INACTIVE` | 다음 `version_no`의 `DRAFT` 생성 | `STATE_CONFLICT` |
| 그래프 저장 | 버전 `DRAFT` | 노드/옵션 replace | `STATE_CONFLICT` |
| 게시 | 버전 `DRAFT` | 기존 `PUBLISHED`는 `ARCHIVED`, 대상은 `PUBLISHED` | `STATE_CONFLICT`, `VALIDATION_ERROR` |
| 활성화 | 시나리오 `DRAFT`, `INACTIVE` + 게시 버전 존재 | `ACTIVE`, `active_version_id` 지정 | `STATE_CONFLICT` |
| 비활성화 | `ACTIVE` | `INACTIVE` | `STATE_CONFLICT` |

### 3.4 감사 로그

서비스 명령 단위로 아래 이벤트를 기록한다.

| 이벤트 | target_type | target_id | detail |
|---|---|---|---|
| `SCENARIO_CREATE` | `scenario` | scenario id | after |
| `SCENARIO_UPDATE` | `scenario` | scenario id | before/after |
| `SCENARIO_DELETE` | `scenario` | scenario id | before/after |
| `SCENARIO_VERSION_SAVE` | `scenario_version` | version id | nodeCount, optionCount |
| `SCENARIO_VERSION_PUBLISH` | `scenario_version` | version id | before/after, archivedVersionIds |
| `SCENARIO_ACTIVATE` | `scenario` | scenario id | before/after |
| `SCENARIO_DEACTIVATE` | `scenario` | scenario id | before/after |
| `SCENARIO_KEYWORD_SAVE` | `scenario` | scenario id | keywordCount, synonymCount |

`AuditTrailRecorder`는 비밀번호, 세션 ID, CSRF 토큰, API 키를 기록하지 않는다.

테스트 컨테이너 패턴:

```java
@Container
static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine");

@DynamicPropertySource
static void registerProperties(DynamicPropertyRegistry registry) {
    registry.add("spring.datasource.url", postgres::getJdbcUrl);
    registry.add("spring.datasource.username", postgres::getUsername);
    registry.add("spring.datasource.password", postgres::getPassword);
}
```

## 5. 추가 수용 기준

- Flyway V3와 V3.1이 PostgreSQL에서 clean schema 기준으로 성공한다.
- `/admin/scenarios` 목록, 등록, 상세, 미리보기 화면이 ADMIN/OPERATOR 권한으로 접근된다.
- `/admin/api/**`의 401/403/400/409 응답은 공통 JSON 형식을 따른다.
- V3.1 적용 후 기존 ADMIN은 `must_change_password=false`, OPERATOR 시드는 `enabled=false`, `must_change_password=true` 기준을 충족한다.
- 같은 시나리오에 `PUBLISHED` 버전이 동시에 2개 존재하지 않는다.
- 게시된 버전 저장 요청은 `STATE_CONFLICT`로 실패한다.
- 시작 노드 누락 또는 도달 불가능 노드가 있는 버전은 게시할 수 없다.
- 키워드/유사어 일괄 저장은 트랜잭션으로 처리되고 실패 시 이전 데이터가 유지된다.
- 감사 로그 detail은 대상 ID와 before/after 또는 변경 건수를 포함한다.
- `mvn test`가 성공한다.

## 7. 영향 범위 매트릭스

| 영역 | 영향 | 주의 |
|---|---|---|
| DB | V3 테이블 7개, FK, 인덱스 추가. V3.1에서 `users.must_change_password` 추가 | V3는 기존 V1/V2 테이블을 수정하지 않는다. V3.1만 인증 테이블을 보완한다. |
| 인증/인가 | OPERATOR 시딩, `/admin/**` 권한 확장 | ADMIN 전용 메뉴는 권한 분기 유지 |
| CSRF | 쿠키 기반 CSRF 토큰 노출 | API 호출 스크립트에서 헤더 전송 필요 |
| 쿠키 | `SameSite=Lax`, `Secure=true`, `HttpOnly=true` 기본 | CSRF 토큰 쿠키는 `HttpOnly=false` 예외 |
| 인프라 | `forward-headers-strategy=framework`, prod 전용 부팅 경고 | nginx `X-Forwarded-*` 설정 확인 |
| 사용자 테이블 | `must_change_password` 컬럼 추가 | 기존 ADMIN은 기본값 false, OPERATOR 시드는 true |
| 감사 | 직접 기록용 컴포넌트 추가 | 기존 AOP 제거 금지 |
| 화면 | 관리자 시나리오 화면 3종 추가 | 대형 그래프 에디터는 M2 범위 제외 |
| 테스트 | Testcontainers 통합 테스트 추가 | 공유 컨테이너 사용 |

## 8. 위험 및 확인 필요 사항

- OPERATOR 운영 기본 계정은 비활성 시딩과 최초 비밀번호 변경 강제로 확정했다. 정식 사용자 관리 UI는 M6에서 확장한다.
- 미리보기는 M2 서버 렌더 시뮬레이터이므로 M3 챗봇 위젯 도입 시 교체 범위를 다시 산정해야 한다.
- `condition_expr`는 저장만 하고 실행하지 않는다. 실행 규칙은 M3 또는 M4에서 별도 설계한다.
- 키워드 검색 품질, 유사어 추천, 랭킹은 M4 검색 설계로 이관한다.
- 그래프 대량 편집 UX는 M2에서 textarea 또는 단순 폼으로 시작하고, 복잡한 시각 편집기는 후속 범위로 둔다.
