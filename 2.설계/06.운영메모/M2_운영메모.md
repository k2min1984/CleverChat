# M2 운영 메모

> 작성일: 2026-05-08
> 범위: 시나리오 도메인 도입 시 운영 확인사항

## 1. 배포 전 확인

- Flyway `V3__scenario_baseline.sql`이 stage DB에서 성공하는지 확인한다.
- Flyway `V3_1__auth_must_change_password.sql`이 `users.must_change_password`만 추가하는지 확인한다.
- 기존 M1 로그인/세션/감사 로그 동작이 회귀되지 않는지 확인한다.
- ADMIN/OPERATOR 권한별 메뉴와 URL 접근 제어를 확인한다.
- 운영 기본 OPERATOR 계정은 비활성 상태로 생성되고 `must_change_password=true`인지 확인한다.
- 쿠키 기본 속성이 `SameSite=Lax`, `Secure=true`, `HttpOnly=true`인지 확인한다. CSRF 토큰 쿠키만 `HttpOnly=false` 예외다.
- `server.forward-headers-strategy=framework`가 적용되고, 관련 부팅 경고 로그는 prod 프로파일에서만 출력되는지 확인한다.
- 시나리오 생성/수정/삭제/게시/활성화 감사 로그가 남는지 확인한다.

## 2. 운영 데이터 기준

| 데이터 | 기준 |
|---|---|
| 카테고리 | 초기에는 운영자가 화면에서 직접 생성 |
| 시나리오 버전 | 게시된 버전은 수정 금지, 새 초안 생성 |
| 삭제 | 논리 삭제 기준 |
| 활성 버전 | 시나리오별 1개만 운영 |
| 키워드/유사어 | M4 검색 품질 개선의 기본 데이터로 사용 |

## 3. OPERATOR 활성화 절차

1. 운영 기본 OPERATOR 계정은 배포 시 `enabled=false`, `must_change_password=true` 상태로만 시딩한다.
2. ADMIN 권한 사용자가 운영 승인 요청자와 계정 소유자를 별도 채널로 확인한다.
3. ADMIN 화면 또는 운영 SQL 절차로 대상 OPERATOR의 `enabled` 값을 `true`로 변경한다. 이때 `must_change_password=true`는 유지한다.
4. 임시 비밀번호는 계정 소유자에게 일회성 채널로 전달하고, 최초 로그인 후 `/admin/password-change` 흐름에서 즉시 변경하게 한다.
5. 활성화, 최초 로그인, 비밀번호 변경 성공 여부를 `login_log`와 `audit_log`에서 확인한다.
6. 소유자 확인 실패, 장기 미접속, 퇴사/권한 회수 요청 시 `enabled=false`로 되돌리고 감사 로그를 남긴다.

## 4. 장애 대응 메모

| 증상 | 확인 |
|---|---|
| 시나리오 목록 지연 | `scenario(status, updated_at)` 인덱스 사용 여부 |
| 게시 실패 | 시작 노드, END 노드 옵션, 옵션 연결 검증 |
| 활성화 실패 | 게시 버전 존재 여부 |
| 저장 후 감사 로그 없음 | `@Audited` 적용 여부, AOP 설정 |
| 권한 오류 | 사용자 role과 Security URL 매핑 |
| 초기 OPERATOR 로그인 불가 | 계정 enabled 여부, 비밀번호 변경 플래그, 활성화 절차 |
| 비밀번호 변경 강제 미동작 | V3.1 컬럼 적용 여부, `must_change_password` 값, `/admin/password-change` 필터 예외 |
| 프록시 IP/HTTPS 인식 오류 | nginx `X-Forwarded-*` 헤더와 `forward-headers-strategy` 설정 |

## 5. 로그/백업

- `scenario_*` 테이블은 DB 정기 백업 대상에 포함한다.
- 게시/활성화 이력은 `audit_log`로 추적한다.
- 운영 로그에는 시나리오 본문 전체를 반복 출력하지 않는다.
- 운영 반영 전 stage DB 백업을 수행하고, Flyway 실패 시 애플리케이션 기동을 중단한다.

## 6. 후속 운영 과제

- 시나리오 export/import 절차
- 게시 승인 워크플로우
- 운영 대시보드 지표 연결
- 챗봇 런타임 캐시 무효화 정책
