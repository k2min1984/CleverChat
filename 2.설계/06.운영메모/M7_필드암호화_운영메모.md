# M7 Field Encryption Operations Memo

> Updated: 2026-05-28

## Scope

- Encrypted fields: `chat_message.content`, `chat_feedback.comment`, `chat_failure.review_comment`.
- New writes store ciphertext in `*_ciphertext`, key id in `*_key_id`, and version in `*_encryption_version`.
- Legacy plaintext columns remain for compatibility. New non-null writes use `[encrypted]` as the plaintext placeholder.
- Search logs, notices, audit logs, crawl documents, and popular query aggregation are outside this baseline.

## Key Configuration

- `CLEVERCHAT_FIELD_ENCRYPTION_KEY_BASE64`: required in stage/prod. The decoded value must be exactly 32 bytes.
- `CLEVERCHAT_FIELD_ENCRYPTION_KEY_ID`: optional key identifier, default `local-v1`.
- `CLEVERCHAT_FIELD_ENCRYPTION_PREVIOUS_KEYS`: optional previous-key keyring. Format is `keyId:base64;oldKeyId:base64`.
- Suggested key generation:

```bash
openssl rand -base64 32
```

The key must be stored as an OS environment secret or an equivalent restricted external properties source. Do not commit it to Git, paste it into tickets, or include it in logs.

## Startup Rules

- `stage` and `prod` fail startup when `CLEVERCHAT_FIELD_ENCRYPTION_KEY_BASE64` is missing.
- `dev` and `test` can use the local test key path, but production-like rehearsals should inject the real environment variable shape.
- A restored database must be paired with the same field encryption key that was used when the ciphertext was written.

## Backup And Restore

- Database backups alone are not enough to recover encrypted chat fields. Back up the active key material through the secret-management procedure.
- If the key is lost, ciphertext values cannot be decrypted. Legacy plaintext rows without ciphertext remain readable only if their original plaintext column still exists.
- During restore rehearsal, verify at least one chat history row, feedback row, and reviewed failure row through the application, not only by SQL.

## Rotation And Backfill Limits

- Current implementation records `key_id` and encryption version and provides manual maintenance APIs for legacy plaintext backfill and key rotation.
- Rotation reads old ciphertext with `CLEVERCHAT_FIELD_ENCRYPTION_PREVIOUS_KEYS`, writes with the active key, and records the active key id.
- Existing plaintext rows are intentionally not encrypted by Flyway because Flyway does not have access to runtime key material.
- Backfill and rotation API calls write sanitized audit records with action `FIELD_ENCRYPTION_BACKFILL` or `FIELD_ENCRYPTION_ROTATE`.
- Audit detail is limited to `dryRun`, `limit`, `scanned`, `updated`, `skipped`, and `failed`.

## Manual Maintenance APIs

All requests use the existing admin API authentication and CSRF rules.

Backfill legacy plaintext rows:

```http
POST /admin/api/security/field-encryption/backfill
Content-Type: application/json

{ "dryRun": true, "limit": 500 }
```

Rotate previous-key ciphertext rows:

```http
POST /admin/api/security/field-encryption/rotate
Content-Type: application/json

{ "dryRun": true, "limit": 500 }
```

Response fields:

- `scanned`: candidate rows read across `chat_message`, `chat_feedback`, and `chat_failure`.
- `updated`: rows successfully rewritten.
- `skipped`: reserved for future policy skips.
- `failed`: rows that could not be decrypted or rewritten. The response does not include plaintext, ciphertext, or key material.

Operational order:

1. Set the new active key in `CLEVERCHAT_FIELD_ENCRYPTION_KEY_BASE64` and `CLEVERCHAT_FIELD_ENCRYPTION_KEY_ID`.
2. Put the prior active key in `CLEVERCHAT_FIELD_ENCRYPTION_PREVIOUS_KEYS`.
3. Restart the app and run rotation with `dryRun=true`.
4. Run rotation with `dryRun=false` in bounded batches.
5. Run backfill with `dryRun=true`, then `dryRun=false` for legacy plaintext rows.
6. Keep old keys until dry-run returns zero candidates and restore rehearsal confirms encrypted rows can be read.

## Incident Checks

- Do not log request body, query string, SQL parameters, plaintext content, ciphertext key material, or Base64 keys while investigating decryption errors.
- Do not put plaintext, ciphertext, key id, Base64 keys, or request body content into `audit_log.detail`.
- To verify maintenance execution, filter `/admin/audit-logs` by actor and action `FIELD_ENCRYPTION_BACKFILL` or `FIELD_ENCRYPTION_ROTATE`, then compare only the summarized counts with the API response.
- `DATA_DECRYPTION_FAILED` means the application could not read an encrypted field. Check key id, active environment variables, deployment history, and backup/restore pairing before retrying.
