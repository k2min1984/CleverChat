## 1. 확정 결정값

- 대화 상태는 `chat_session` DB 테이블에 저장한다.
- `anonymous_id` 등 식별 쿠키는 `SameSite=Lax`, `Secure=true`, `HttpOnly=true`를 기본으로 한다.
- `server.forward-headers-strategy=framework`를 사용하고 prod 프로파일에서만 프록시 헤더 부팅 경고를 남긴다.
- 키워드/유사어 매칭 캐시 TTL 기본값은 300초다.
- 세션은 마지막 활동 후 30분 미입력 시 만료한다.
- 대화 이력, 메시지, 피드백, 실패 기록은 90일 보존 후 파기한다.
- fallback 검색 고도화와 알림 채널은 M4/M6에서 확정한다.

## 2. 만료 배치

| 항목 | 기준 |
|---|---|
| 구현 | Spring `@Scheduled` |
| 주기 | 1분 또는 5분 후보. 초기값 5분 권장 |
| 대상 | `chat_session.state='ACTIVE' AND expires_at < now()` |
| 처리 | `EXPIRED` 상태 갱신, `last_activity_at`은 변경하지 않음 |
| 멱등성 | 이미 `EXPIRED`인 행은 제외하므로 재실행 안전 |
| 건수 상한 | 1회 1,000건 후보 |
| 트랜잭션 | 배치 chunk 단위 트랜잭션 |

검증 쿼리:

```sql
select count(*) as expired_candidates
from chat_session
where state = 'ACTIVE'
  and expires_at < now();
```

처리 쿼리 후보:

```sql
update chat_session
set state = 'EXPIRED'
where id in (
    select id
    from chat_session
    where state = 'ACTIVE'
      and expires_at < now()
    order by expires_at
    limit 1000
);
```

## 3. 90일 파기 배치

| 항목 | 기준 |
|---|---|
| 구현 | Spring `@Scheduled` |
| 주기 | 일 1회 새벽 시간대 |
| 기준 | `chat_session.started_at < now() - interval '90 days'` |
| 일일 처리 한도 | 10,000 세션 후보. 운영 데이터량에 따라 조정 |
| 복구 | 파기 후 애플리케이션 레벨 복구 불가. DB 백업 보존 범위에서만 복구 가능 |

FK 고려 파기 순서:

1. `chat_feedback`
2. `chat_failure`
3. `chat_message`
4. `chat_session`

대상 세션 후보:

```sql
select id
from chat_session
where started_at < now() - interval '90 days'
order by started_at
limit 10000;
```

검증 쿼리:

```sql
select
    count(*) filter (where started_at < now() - interval '90 days') as purge_candidates,
    min(started_at) as oldest_session,
    max(started_at) as newest_session
from chat_session;
```

파기 후 잔여 확인:

```sql
select count(*) as remaining_old_sessions
from chat_session
where started_at < now() - interval '90 days';
```

운영 주의:

- 대량 삭제는 chunk 단위로 처리하고 각 chunk 처리 건수를 로그에 남긴다.
- 파기 대상 ID 목록은 원문 메시지 없이 건수와 기간만 운영 로그에 기록한다.
- 파기 배치 실패 시 다음 실행에서 재시도 가능해야 한다.

## 4. 실패 큐 모니터링

| 지표 | 임계 후보 | 조치 |
|---|---:|---|
| 미처리 `chat_failure` 수 | 100건 초과 | 운영자 확인 요청 |
| 1시간 `NO_MATCH` 수 | 50건 초과 | fallback/키워드 폭주 점검 |
| `SYSTEM_ERROR` 수 | 10건 초과 | 애플리케이션 오류 로그 확인 |

알림 채널은 M6에서 결정한다. M3에서는 로그와 관리자 실패 큐 화면으로 확인 가능하게 둔다.

실패 큐 상세 JSON은 `2.설계/02.DB설계서/M3_챗봇런타임ERD.md`의 `chat_failure.detail` 표준 키 사전을 따른다. 운영 화면에는 `reason`, `inputSummary`, `currentNodeId`, `fallbackSource`, `errorCode`, `piiTypes`, `requestId`만 기본 노출하고, 원문 입력·IP·User-Agent·세션 식별자·stack trace는 노출하지 않는다.

## 5. SLO 후보

| 항목 | 후보값 | 산식 |
|---|---:|---|
| 답변 실패율 | 일간 5% 이하 | `NO_MATCH + SYSTEM_ERROR` / 사용자 입력 수 |
| 다운투표율 | 일간 10% 이하 | `DOWN` / 전체 피드백 수 |
| 세션 완료율 | 일간 60% 이상 | `COMPLETED` / 전체 종료 세션 |
| fallback 비율 | 일간 20% 이하 | fallback 응답 수 / 사용자 입력 수 |
| API p95 응답 | 500ms 이하 후보 | `/chat/api/**` 서버 처리 시간 |

SLO는 운영 데이터 확보 전 후보값이며 M6 대시보드에서 조정한다.

### 5.1 M3 구현 로그/지표 기준

| 구분 | 필수 필드 | 금지 필드 |
|---|---|---|
| 세션 시작 | `scenarioId`, `versionId`, `state`, `elapsedMs`, `requestId` | `anonymous_id` 원문, IP 원문, UA 원문 |
| 진행 요청 | `sessionState`, `currentNodeId`, `matchType`, `elapsedMs`, `requestId` | 사용자 입력 원문, CSRF token |
| 실패 큐 | `reason`, `fallbackSource`, `inputLength`, `piiTypes`, `requestId` | stack trace, 세션 ID, 원문 식별자 |
| 만료 배치 | 후보 건수, 처리 건수, chunk 크기, 소요 시간 | 대상 세션 ID 목록 |
| 파기 배치 | 대상 기간, 삭제 건수, chunk 수, 소요 시간 | 메시지 content, failure detail 원문 |
| 매칭 캐시 | cache name, hit/miss, invalidation reason, scenarioId | 입력 원문 |

M3 구현 PR은 위 필드 기준으로 로그 샘플 또는 테스트 로그 검색 결과를 남긴다. 로그 포맷 자체는 기존 Logback 설정을 우선 사용하고, JSON 로그 전환은 M6 범위로 둔다.

## 7. 트러블슈팅

### 7.1 만료 다발

1. `chat_session(state, expires_at)` 인덱스 사용 여부를 실행계획으로 확인한다.
2. 애플리케이션 시간이 DB 시간과 크게 어긋나지 않는지 확인한다.
3. 클라이언트 전송 실패 또는 CSRF 오류 증가 여부를 로그에서 확인한다.
4. 배치 chunk 크기와 실행 주기를 점검한다.

### 7.2 `anonymous_id` 폭주

1. 동일 IP 해시에서 신규 `anonymous_id` 생성이 급증했는지 확인한다.
2. 쿠키 도메인/path/SameSite/Secure/HttpOnly 설정 변경 여부를 확인한다.
3. 봇 트래픽 또는 브라우저 쿠키 차단 환경을 점검한다.
4. Rate limit 429 발생량을 확인한다.

### 7.3 fallback 폭주

1. 특정 시나리오/노드에서 `NO_MATCH`가 집중되는지 확인한다.
2. 최근 게시된 `scenario_version`의 옵션 라벨과 키워드를 확인한다.
3. M4 검색 stub 오류 또는 빈 결과 증가 여부를 확인한다.
4. 운영자 추천 질문과 시나리오 키워드 보강 후보를 실패 큐에 표시한다.

### 7.4 매칭 캐시 정합성

1. 캐시 TTL이 기본 300초인지 확인한다.
2. 시나리오 게시, 활성/비활성 변경, 키워드/유사어 저장 성공 후 캐시 무효화 로그가 남는지 확인한다.
3. 무효화 훅이 미구현된 초기 단계에서는 TTL 만료 후 정합성이 회복되는지 확인한다.

## 8. 백업·복구 영향

| 대상 | 기준 |
|---|---|
| 신규 테이블 | 일일 DB 백업 포함 |
| RPO | 기존 PostgreSQL 백업 정책을 따름. M3 기준 별도 단축 없음 |
| RTO | 기존 애플리케이션 복구 RTO를 따름 |
| 복구 검증 | 세션/메시지/피드백 FK 정합성 확인 |
| 파기 데이터 | 90일 파기 후 앱 레벨 복구 불가 |

복구 검증 쿼리 후보:

```sql
select count(*) as orphan_messages
from chat_message m
left join chat_session s on s.id = m.session_id
where s.id is null;
```

```sql
select count(*) as orphan_feedback
from chat_feedback f
left join chat_message m on m.id = f.message_id
where m.id is null;
```

## 9. 운영 로그 기준

- 만료 배치: 후보 건수, 처리 건수, 소요 시간, 실패 원인
- 파기 배치: 대상 기간, chunk 수, 삭제 건수, 소요 시간
- 실패 큐: reason별 건수, 미처리 건수
- Rate limit: anonymous_id 원문 제외, IP 해시 기준 집계
- 매칭 캐시: TTL, hit/miss, 무효화 이벤트, 실패 원인
- 프록시 헤더: prod 부팅 시 누락/오설정 경고. dev/stage에서는 경고 출력하지 않음
- 키워드 저장 안내: 관리자 토스트/상태 영역에 노출한 안내 유형(`KW-MSG-01`~`KW-MSG-03`)과 캐시 무효화 결과를 함께 기록한다.

사용자 메시지 원문은 로그에 남기지 않는다.
