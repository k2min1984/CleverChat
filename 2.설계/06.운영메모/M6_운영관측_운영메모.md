# M6 운영 관측 운영메모

## 1차 구현 범위

- 운영 통계 대시보드: `/admin/statistics`
- 운영 통계 API: `GET /admin/api/statistics/summary`
- 감사 로그 조회 화면: `/admin/audit-logs`
- 감사 로그 API: `GET /admin/api/audit-logs`
- API 요청 구조화 로그: `/admin/api/**`, `/chat/api/**`
- 보안 이벤트 구조화 로그: 인증 실패, CSRF 거부, 로그인 성공/실패/잠금
- 이상행위 기본 룰: 관리자 로그인 실패 횟수가 잠금 임계값 직전이면 `LOGIN_FAILURE_SPIKE`, 임계값 도달 시 `LOGIN_LOCKED`를 security 이벤트로 기록

## 통계 기준

- 시간 기준은 Asia/Seoul의 오늘 0시와 최근 7일 시작일이다.
- 지표는 기존 DB 테이블을 직접 집계한다.
- 포함 지표는 채팅 세션, 채팅 메시지, 채팅 실패, 피드백, 검색, PII 차단, 크롤 실패, 미확인 크롤 실패, 활성 시나리오 수다.
- 1차 구현은 카드/표 중심이며 별도 차트 라이브러리나 외부 모니터링 연동은 없다.

## 감사 로그

- 기존 `audit_log` 테이블을 조회한다.
- 필터는 actor, action, targetType, from, to, limit을 지원한다.
- 조회 API는 기존 `ApiResponse` envelope를 유지한다.

## 로그 파일

- `dev`: 콘솔 로그 중심으로 운영하며 구조화 JSON 메시지도 콘솔에 출력한다.
- `stage`, `prod`: `LOG_DIR` 기본값은 `/var/log/cleverchat`이다.
- `app.log`: 일반 애플리케이션 로그, 90일 보존, 총 20GB 제한.
- `api.log`: API access JSON 로그, 90일 보존, 총 20GB 제한.
- `security.log`: 보안 이벤트 JSON 로그, 365일 보존, 총 20GB 제한.
- `error.log`: ERROR 이상 로그, 180일 보존, 총 20GB 제한.

## PII 미기록 원칙

- request body, response body, query string은 파일 로그에 남기지 않는다.
- IP와 User-Agent는 SHA-256 hash만 남긴다.
- `anonymous_id`는 hash만 남기며 원문 cookie 값은 기록하지 않는다.
- 관리자 username은 운영 감사 식별에 필요한 범위에서만 보안 이벤트에 남긴다.

## 운영 확인 절차

- API 장애 확인은 `api.log`의 `requestId`, `path`, `status`, `durationMs`를 기준으로 추적한다.
- 인증/CSRF/로그인 문제는 `security.log`의 `type`, `username`, `path`, `requestId`를 기준으로 확인한다.
- 애플리케이션 예외는 `error.log`를 우선 확인하고, 같은 시간대의 `api.log` requestId와 대조한다.

## 후속 범위

- 이상 행위 탐지 룰 고도화: 관리자 IP 변경, 대량 검색, API 5xx 반복, DB 기반 룰 히스토리
- 외부 로그 수집기/대시보드 연동
- 외부 알림 provider별 payload/template 고도화
- 백업 자동 실행 에이전트와 외부 스토리지 연동

## M6 External Notification Webhook Baseline

- v1 external notification uses generic outbound webhook channels managed at `/admin/notifications`.
- Webhook endpoints are resolved from `notification_channel.endpoint_env_key`; the actual URL/token must stay in OS env or equivalent external configuration and is never stored in DB.
- Supported channel types are `WEBHOOK`, `SLACK_WEBHOOK`, and `EMAIL_SMTP`. `SLACK_WEBHOOK` sends a Slack Incoming Webhook-compatible JSON payload only; Slack OAuth/Web API is out of scope.
- `EMAIL_SMTP` uses Spring Mail SMTP configuration. Set `spring.mail.host`, SMTP auth properties as needed, `cleverchat.notification.email.from`, and an email recipient env key such as `OPS_ALERT_EMAIL_TO`.
- Secret rotation uses optional `previous_endpoint_env_key`. During rotation, keep the old webhook URL in the previous env key until a test send succeeds with the new primary env key, then clear the previous key.
- First automatic event source is crawl failure (`CRAWL_RUN_FAILED` from `crawl_run_log`). Repeated API 5xx and login lock events remain schema-ready follow-up connections.
- Payloads contain only event id, event type, severity, summary, admin URL, and created time. Chat message content, request/response bodies, query strings, raw IP, raw User-Agent, and encryption key material must never be included.
- Delivery records are kept in `notification_event` with status, attempt count, last error summary, next retry time, and reviewed state. Same open source event is reused to avoid duplicate rows.
- Retry policy baseline is at most 3 attempts with bounded backoff, then `FAILED` until an admin reviews the event. External notification failure must not fail the original crawl transaction.
- Retry worker baseline: `OpsNotificationService.retryDueEvents` runs every 60000ms by default through `cleverchat.notification.retry.fixed-delay-ms` and processes open `RETRY` events where `next_retry_at <= now` and `attempt_count < 3`.
- Admin flow baseline: list channels/events, create/update webhook, Slack-compatible webhook, or email SMTP channel, send test notification, and mark events reviewed.
- Provider-specific payload mapping, HTML email templates, and recipient group management remain follow-up work.

## M7 보안 헤더 연계

- 공통 보안 헤더와 CSP 운영 기준은 [M7_보안헤더_운영메모.md](./M7_보안헤더_운영메모.md)를 따른다.
- API/security 로그는 요청/응답 본문과 query string을 남기지 않으며, 보안 헤더 점검도 헤더 존재 여부 중심으로 수행한다.
## M7.4 Performance Operations

- `slow-query.log` is written in `stage` and `prod` when a MyBatis statement takes at least `cleverchat.ops.slow-query-threshold-ms` milliseconds. The default is 1000ms.
- Slow query log fields are limited to timestamp, event, requestId, statementId, operation, durationMs, and success. SQL text and bind parameters are intentionally omitted.
- When repeated slow entries appear, correlate `requestId` with `api.log`, then run `EXPLAIN (ANALYZE, BUFFERS)` manually in a safe database session.
- Matching cache is local Caffeine only. In a multi-node deployment, treat cache coherence as eventually refreshed by TTL unless Redis is introduced later.
- Pre-release load checks use the k6 baseline in `4.테스트/03.성능/k6-baseline.js`.

## M6 Notice, Backup, and Rollback Baseline

- Notice management is available at `/admin/notices`; API writes use the existing admin CSRF and `ApiResponse` contract.
- Chat users see only enabled notices where the current server time is within `starts_at` and `ends_at`; no public notice API is exposed.
- Notice deletion is soft-disable (`enabled=false`) so past operational messages remain auditable.
- Database backup is an operations task, not an application job. Run `pg_dump` before production Flyway migrations and before data-destructive maintenance.
- Minimum initial target: daily logical backup, weekly restore rehearsal in a non-production PostgreSQL instance, and manual verification of table counts after restore.
- If Flyway fails during deployment, stop the new application instance, keep the failed schema unchanged for diagnosis, and restore from the pre-deploy backup only after confirming rollback is required.
- Application rollback means redeploying the previous JAR/config pair. Database rollback is backup restore based; down migrations are not assumed.

## Redis Rate Limit Operations

- Chat rate limiting supports optional Redis mode through `cleverchat.chat.rate-limit.store=redis`; keep `memory` mode for single-node deployments.
- Configure Redis with Spring Boot `spring.data.redis.*` properties and keep `cleverchat.chat.rate-limit.max-requests` / `window-seconds` aligned across nodes.
- Rate limit Redis keys use hashes; anonymous/session raw identifiers must not appear in Redis keys or logs.
- Redis failures are fail-open for chat availability and log `RATE_LIMIT_REDIS_UNAVAILABLE` only.
- Scenario matching Caffeine cache remains local TTL-based; Redis cache conversion is follow-up work.

## External Log Collection Baseline

- Filebeat sample config is provided at `3.개발/cleverchat/deploy/filebeat-cleverchat.yml`.
- Channel manifest is maintained at `M6_log_collection_manifest.md`.
- `api.log`, `security.log`, and `slow-query.log` are JSON-line channels for external parsing.
- `app.log` and `error.log` remain text channels for general application and ERROR level logs.
- Collectors should read `/var/log/cleverchat/*.log` in stage/prod and should not inject request/response bodies, query strings, raw IP, raw User-Agent, PII, webhook URLs, SMTP secrets, API keys, or encryption key material.
- Operational correlation starts from `api.log.requestId`, then checks matching `error.log`, `slow-query.log`, or `security.log` entries.
- ELK/OpenSearch/Loki servers, dashboards, alert rules, and long-term archive storage remain follow-up infrastructure work.

## Backup Automation Agent Baseline

- PostgreSQL backup samples are provided under `3.개발/cleverchat/deploy/backup/`.
- Formal backup and recovery deliverables are maintained under `5.배포/05.백업복구절차서/`:
  - `백업정책.md`
  - `PITR_복구절차.md`
  - `복구리허설_체크리스트.md`
- Backup execution stays outside the application process and should run from OS scheduler, systemd timer, cron, or Windows Task Scheduler.
- Scripts read DB connection settings from `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, and `PGPASSWORD`.
- Each run creates a timestamped PostgreSQL custom-format dump using `pg_dump -Fc --no-owner --no-acl` and a `.sha256` checksum file.
- Default retention is 14 days, with a minimum of 7 days through `CLEVERCHAT_BACKUP_RETENTION_DAYS`.
- Run a fresh backup before production Flyway migrations, data-destructive maintenance, field-encryption backfill, and key rotation maintenance.
- Restore rehearsal should first check `pg_restore --list`, then restore into a non-production database and verify Flyway history, table counts, admin login, scenario list, chat history, feedback, crawl/search operations, and notification events.
- Encrypted chat fields require the matching `CLEVERCHAT_FIELD_ENCRYPTION_KEY_BASE64`, `CLEVERCHAT_FIELD_ENCRYPTION_KEY_ID`, and any previous keys. Database backup alone is not enough for encrypted field recovery.
- If Flyway fails, preserve the failed database for diagnosis and restore only after a rollback decision is approved.
- External storage upload, backup encryption at rest, backup success/failure notifications, and scheduler registration files remain follow-up infrastructure work.
