## 1. 확정 결정값

- 비로그인 사용자는 HttpOnly `anonymous_id` 쿠키(UUID, 1년)로 식별하고, 쿠키 속성은 전 프로파일에서 `SameSite=Lax`, `Secure=true`, `HttpOnly=true`를 기본으로 한다.
- 대화 상태와 이력은 DB에 저장하고 90일 후 파기한다.
- free-text와 feedback comment는 입력 검증, PII 탐지, 출력 이스케이프를 거친다.
- 챗봇 페이지는 전용 페이지 우선이며 외부 임베드는 M3에서 허용하지 않는다.

## 2. `anonymous_id` 쿠키

| 속성 | 기준 |
|---|---|
| 이름 | `anonymous_id` |
| 값 | UUIDv4 또는 서명된 UUID |
| 만료 | 1년 |
| `HttpOnly` | true |
| `Secure` | true |
| `SameSite` | `Lax` |
| 경로 | `/` 또는 `/chat` |

주의:

- 쿠키 값은 로그에 남기지 않는다.
- 쿠키 분실 시 새 사용자로 취급한다.
- IP/UA 해시는 사용자 추적의 보조 지표이며 본인 인증 수단으로 쓰지 않는다.
- 로컬 개발에서 HTTPS 없이 검증해야 하는 경우만 별도 개발 override를 명시적으로 둔다. 운영 기준 문서는 `Secure=true`를 단일 기준으로 유지한다.

## 3. 본인 세션 검증

| API | 검증 |
|---|---|
| `/chat/api/sessions/{id}` | 쿠키 `anonymous_id`와 `chat_session.anonymous_id` 일치 |
| `/chat/api/sessions/{id}/select-option` | 본인 검증 + `ACTIVE` 상태 |
| `/chat/api/sessions/{id}/free-text` | 본인 검증 + `ACTIVE` 상태 |
| `/chat/api/sessions/{id}/history` | 본인 검증 |
| `/chat/api/sessions/{id}/end` | 본인 검증 |
| `/chat/api/messages/{messageId}/feedback` | 메시지 → 세션 → `anonymous_id` 일치 |

불일치 시 403 + `CHAT_SESSION_FORBIDDEN`을 반환한다. 존재하지 않는 세션과 본인 아님을 화면에서 과도하게 구분하지 않는다.

## 4. CSRF

- M2와 동일하게 쿠키 기반 CSRF 토큰을 사용한다.
- 비로그인 사용자 API도 상태 변경 요청은 CSRF 검증을 통과해야 한다.
- 누락 또는 불일치 시 403 JSON을 반환한다.
- CSRF 토큰은 감사 로그, 운영 로그, 오류 응답에 포함하지 않는다.
- CSRF 토큰 쿠키는 JS 헤더 전송을 위해 `HttpOnly=false` 예외를 둔다. `Secure=true`, `SameSite=Lax`는 동일 적용한다.

## 5. 입력 검증

| 입력 | 제한 | 정책 |
|---|---:|---|
| `freeText` | 1~500자 | 제어문자, HTML 태그, 스크립트 패턴 금지 |
| `feedback.comment` | 0~1,000자 | 선택값. HTML 입력 금지 |
| `optionId` | 양수 Long | 현재 노드 옵션인지 서비스 검증 |
| `scenarioId` | 양수 Long | 활성 시나리오와 `PUBLISHED` 버전 검증 |
| 관리자 필터 | allow-list | 상태 enum, 기간 범위, size 상한 |

HTML 입력은 저장 전 거절을 기본으로 한다. 화면 출력은 Thymeleaf `th:text` 기본 escape를 사용한다.

## 6. PII 정책

탐지 대상:

| 유형 | 예시 정책 |
|---|---|
| 주민등록번호 패턴 | 차단 또는 마스킹 |
| 카드번호 패턴 | 차단 또는 마스킹 |
| 이메일 | 마스킹 |
| 전화번호 | 마스킹 |
| 계좌번호 후보 | 마스킹 후보. 오탐 가능성 법무/운영 검토 |

M3 기본 정책:

- 주민등록번호 후보와 Luhn 검증을 통과한 카드번호 후보는 저장 전 차단하고 `CHAT_PII_BLOCKED`를 반환한다.
- 이메일과 전화번호는 저장 전 마스킹한 값만 `chat_message.content`와 `chat_failure.detail.inputSummary` 후보로 사용한다.
- PII 차단 시 사용자 입력 원문은 `chat_message`, 감사 로그, 운영 로그, failure detail에 저장하지 않는다.
- 계좌번호 후보는 M3 자동 차단 범위에서 제외하고, 운영/법무 확인 후 M6 또는 M7에서 추가한다.
- 최종 차단/마스킹 기준이 바뀌면 `M3_챗봇런타임ERD.md`, `M3_챗봇런타임API.md`, `M3_챗봇런타임_테스트케이스.md`를 함께 갱신한다.

IP/UA:

- IP와 User-Agent 원문은 런타임 테이블에 저장하지 않는다.
- `SHA-256(serverSalt + value)` 해시로 저장한다.
- 서버 솔트는 환경변수 또는 외부 properties에서 주입하고 소스에 커밋하지 않는다.

## 7. 출력 인코딩

- Thymeleaf는 `th:text`를 사용한다.
- `th:utext`는 챗봇 메시지, feedback comment, fallback 카드에 사용 금지한다.
- JSON 응답은 문자열로 내려가더라도 클라이언트에서 `innerHTML` 삽입을 금지하고 `textContent` 또는 템플릿 escape를 사용한다.
- 링크가 필요한 경우 서버가 허용한 내부 경로만 구조화 필드로 제공한다.

## 8. 로그 마스킹

| 로그 | 기준 |
|---|---|
| 감사 로그 | 사용자 메시지 원문 저장 금지. 대상 ID와 처리 결과 중심 |
| 운영 로그 | 사용자 content는 100자 이하 마스킹 요약 |
| 오류 로그 | stack trace는 서버 로그만. 응답에는 오류 코드만 |
| API 요청 로그 | 쿠키, 세션 ID, CSRF 토큰, 원문 PII 제외 |

## 9. Rate Limit

- 기본값: `anonymous_id` 기준 분당 30건.
- application property 후보: `cleverchat.chat.rate-limit-per-minute=30`
- 초과 시 429 + 공통 오류 코드 `RATE_LIMIT_EXCEEDED`를 반환한다.
- 관리자 API는 세션 VO(AuthenticatedUser) 인증 사용자 기준으로 별도 제한을 M6에서 확정한다.

## 10. SSRF/봇 방어

- M3 fallback은 내부 stub만 호출한다.
- 사용자 입력 URL을 서버가 외부로 요청하지 않는다.
- 추천/검색 호출은 내부 서비스 인터페이스로 제한한다.
- 삽입형 위젯은 M3에서 제공하지 않으므로 외부 도메인 CORS 허용을 추가하지 않는다.
- M5 크롤링은 별도 관리자 기능이며 `localhost`/private IP를 기본 차단한다. 개발 검증에서 로컬·내부망 문서를 챗봇 fallback 대상으로 확인해야 할 때만 `CLEVERCHAT_CRAWL_ALLOWED_HOSTS` exact host allowlist를 사용한다.

## 11. 보안 헤더

기존 M1/M2 보안 헤더를 유지한다.

| 헤더 | 기준 |
|---|---|
| HSTS | prod HTTPS에서 유지 |
| X-Frame-Options | `DENY` 또는 기존 정책 유지 |
| CSP | inline script 최소화, 외부 도메인 미허용 |
| X-Content-Type-Options | `nosniff` |
| Referrer-Policy | `strict-origin-when-cross-origin` 후보 |

챗봇 페이지 임베드는 M3에서 차단한다. 위젯 지원 시 CSP, CORS, frame-ancestors를 별도 설계한다.

## 12. 관리자 보안

- `/admin/api/chat/**`는 ADMIN/OPERATOR만 접근한다.
- 관리자 상세 화면에는 `anonymous_id`, IP 원문, UA 원문을 표시하지 않는다.
- 실패 큐 처리 이벤트는 감사 로그에 남긴다.
- feedback comment도 사용자 입력이므로 목록 화면에서 escape한다.

## 13. 법무/운영 확인 필요

| 항목 | 기본안 | 확인 필요 |

## Implementation Note (2026-05-27)
- `/chat/api/**` stores only hashed IP/User-Agent.
- Free-text blocks email, phone, and resident registration number patterns before message persistence.
- Expired sessions return `410 SESSION_EXPIRED`; anonymous/session rate limiting records `RATE_LIMITED` failures.
- The admin failure queue exposes a short session key instead of raw `chat_session.id` or `anonymous_id`.
- Admin feedback list follows the same short session key rule; recommendation operations do not expose user identifiers.
- `SecurityHeadersFilter` applies the common CSP and browser security headers to `/chat`, `/chat/api/**`, admin routes, and `/actuator/health`.
- The CSP does not allow external domains by default. Chat widget embedding remains blocked by `frame-ancestors 'none'` until a separate widget/CORS/CSP design is approved.

## 13. M7.3 PII Masking Baseline (2026-05-27)

- Chat free-text blocks high-risk PII (`RRN`, Luhn-valid `CARD`) before saving a user message and records only non-raw metadata in the failure queue.
- Chat free-text masks low-risk PII (`EMAIL`, `PHONE`) before storing the user message, scenario matching, and M4 fallback search.
- Search input remains stricter than chat input: any detected PII type is blocked and the raw query is not stored in `search_log` or `search_block_log`.
- Low-risk PII masking is still applied before matching/search fallback. New chat message, feedback comment, and failure review comment writes are also protected by M7.4 field encryption at persistence time.

## 14. M3 History and Feedback Implementation Note (2026-05-27)

- Session history APIs use `anonymous_id` cookie ownership checks before returning messages.
- `GET /chat/api/history` returns an empty list when the cookie is missing or invalid and does not force a new identifier only for history lookup.
- Feedback is accepted only for BOT messages that belong to the current `anonymous_id`.
- Feedback comments are limited to 1000 characters and pass through the same PII guard: high-risk values are rejected, low-risk email/phone values are masked before persistence.

## 15. M7.4 Field Encryption Implementation Note (2026-05-28)

- New `chat_message.content`, `chat_feedback.comment`, and `chat_failure.review_comment` writes are encrypted with application-level AES-256-GCM before database persistence.
- Plaintext compatibility columns remain for legacy rows, but new non-null values store `[encrypted]` in those columns and put the encrypted envelope in `*_ciphertext`.
- Runtime history, admin session detail, admin feedback, and admin failure review views decrypt values for authorized responses. If ciphertext is absent, legacy plaintext fallback is used.
- Key management is OS env based: `CLEVERCHAT_FIELD_ENCRYPTION_KEY_BASE64` and `CLEVERCHAT_FIELD_ENCRYPTION_KEY_ID`. External KMS/Vault integration and legacy backfill are separate follow-up tasks.

## 16. M3 Embed Widget Launcher Baseline (2026-05-28)

- The embed baseline is launcher-only: external pages may open `/chat` in a new window.
- iframe embedding remains blocked by `frame-ancestors 'none'` and `X-Frame-Options: DENY`.
- External `/chat/api/**` calls remain disallowed; CORS, CSRF, and same-origin API boundaries are unchanged.
- The launcher sample must not include iframe markup, `/chat/api/**` calls, embed tokens, secrets, or PII query-string examples.

## 17. M9 AI Answer Suggestion Scaffold (2026-05-28)

- AI answer suggestion is disabled by default and does not call an external provider in the scaffold.
- The prompt source is the safe text after existing chat PII guard processing.
- Provider request body, raw personal data, API keys, and provider secrets must not be logged or stored.
- Real provider integration requires a separate review for timeout, rate limit, citation policy, and operator enable controls.

## 18. M10 External REST API Scaffold (2026-05-28)

- `/external/api/v1` is disabled by default and exposes only a non-business status stub.
- API key verification uses SHA-256 hash comparison against `CLEVERCHAT_EXTERNAL_API_KEY_SHA256`.
- The raw API key, request body, query string, and business data must not be logged or returned by the scaffold.
- CORS remains closed until a separate allowlist and abuse-control design is approved.
