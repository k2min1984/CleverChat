# CLEVER 플랫폼 연동 가이드 v1.0 — 신규 시스템 편입 표준

작성: 2026-09-22, CLEVER GATEWAY 팀
지위: **표준.** 신규 시스템을 CLEVER 플랫폼에 연동할 때 이 문서의 계약을 이행한다.
권한 체계의 정본은 **PERM_SPEC_v2.0.md** 이며, 충돌 시 정본을 따른다.
대상: 플랫폼에 편입하려는 모든 시스템 (제품 · 엔진 · 파이프라인)

---

## 0. 한 장 요약

CLEVER 플랫폼 편입의 조건은 **"독립 기동"이 아니라 "신원 수신 계약 이행"** 하나다.
대부분의 시스템은 독립 기동하므로 전제는 이미 충족되어 있고, 실제 관문은 아래 셋이다.

| 관문 | 요구 | 미충족 시 |
|---|---|---|
| ① 신원 수신 | 게이트웨이가 준 신원으로 자체 세션을 만든다 | 편입 불가 — 사용자가 두 번 로그인하게 된다 |
| ② 서브패스 서빙 | `/시스템id/` 아래에서 동작한다 | 경로 편입 불가 — URL 직행(external) 형태로만 연결 |
| ③ 자체 계정 제거 | 통합 구축에서 자기 계정·비밀번호를 보관하지 않는다 | 계정 이원화 — 사실상 편입 실패 |

③ 이 가장 자주 걸린다. **통합 구축 현장에서 제품은 비밀번호를 보관하지 않는다.**
(단독 판매용 자체 계정은 `출처=LOCAL` 로 남길 수 있고, 통합 현장에는 존재하지 않는다.)

역할 분담:

| 주체 | 작업량 |
|---|---|
| 게이트웨이 | 서비스 등록 1건 (관리자 화면 입력) — **코드 수정 없음** |
| 편입 시스템 | 신원 수신 + 서브패스 서빙 + (해당 시) 자체 계정 제거 |

## 1. 플랫폼 현황

### 1.1 정체성

CLEVER GATEWAY 는 **배포 미들웨어이자 통합 프론트엔드**다.

- 사용자는 셸(Electron exe) **하나만 설치**하고, 어떤 서비스가 보이고 어디로 연결되는지는
  게이트웨이가 실시간 결정한다.
- **모든 제품 경로는 단일 오리진 `:30800` 아래**로 편입된다 (`/meeting/`, `/compass-api/` …).
- **게이트웨이 UI(portal-web, Vue3)가 전 제품 기능을 직접 탑재**하고, 제품 자체 UI 는
  게이트웨이를 쓸 수 없는 상황의 **폴백**이다. 즉 편입 시스템에 기대하는 1순위는 화면이 아니라 **API** 다.
- 전제: **폐쇄망**. 외부 인증 솔루션(Keycloak 등) 도입 불가 — 인증은 자체 구현만 쓴다.

### 1.2 구성

| 요소 | 내용 |
|---|---|
| 컨테이너 | `gateway`(nginx :30800) · `auth`(인증·포털 API·잡 엔진) · `admin`(설정 API) |
| 저장소 | SQLite (호스트 볼륨 `data/`) — 사용자·디바이스토큰·문서함·업무·통계 |
| 인증 | 사번 + 비밀번호, 세션 JWT 60분, 디바이스 토큰 30일(무감 재발급), OTP(TOTP 자체 구현) |
| 프록시 | 서비스 저장 시 nginx 조각 자동 생성 → 감시 루프가 `nginx -t` 후 무중단 reload |

### 1.3 현재 편입된 시스템

| id | 성격 | 편입 방식 | SSO |
|---|---|---|---|
| `meeting` (회의록) | 제품 | 경로 프록시 `/meeting/` | ON — 계약 이행 완료, **참조 구현** |
| `nova` (문서 QA/RAG) | 제품 | external (URL 직행, 전환기) | OFF — v2 재구축 중 |
| `compass` (업무 판단·일정) | 제품 폴백 UI | external | OFF |
| `compass-api` | 시스템 브릿지 | 경로 `/compass-api/` (메뉴 비노출) | ON |
| `nova-api` | 시스템 브릿지 | 경로 `/nova-api/` (메뉴 비노출) | ON |
| `/llm-api/`, `/vlm-api/` | LLM·VL 엔진 브릿지 | 수동 nginx 조각 (서비스 아님) | 게이트만 |

> "제품"은 서비스 카드로 노출되고, "브릿지"는 포털 UI 전용 API 통로이며 메뉴에 뜨지 않는다.
> 이 구분이 2장의 편입 유형 선택지와 그대로 대응한다.

### 1.4 포털이 이미 직접 갖고 있는 기능

**편입 전에 반드시 확인할 표다.** 여기 있는 기능을 또 들고 들어오면 사용자에게는 같은 기능이
두 벌로 보이고, 통합 프론트엔드 방침과 충돌한다.

| 화면 | 기능 |
|---|---|
| AI 채팅 | 자유 채팅(LLM 직결 SSE 스트리밍) + 업무 판단(규칙팩·문서 근거 결합) + 대화 저장 |
| 회의록 | 목록·새 회의·녹음 화면(녹음→업로드→AI 작성) |
| 일정 | 전사·부서·개인 3계층, 회차 완료 |
| 문서함 | 폴더·업로드·인덱싱·검색·보고서·PC 폴더 연동 |
| 업무 자동화 | 업무(works) 등록·실행 이력 — 처리기 `report`/`minutes`/`cycle`/`screening` |
| 내 사이클 · 사이클 관리 | 데이터 플로우(그래프) 편집·배포·버전 |
| 업무 규칙(팩) 관리 · 프롬프트 관리 | 버전·승인·활성화·롤백 |
| 이용 통계 | 접속·서비스별·제품 지표 대시보드 |

### 1.5 권한 평면

4층 구조이며 **L1~L3 은 게이트웨이 완비, L4 는 제품 자치**다.

```
게이트웨이                                      편입 시스템
├─ L1 계정·인증 (사번·비밀번호·OTP·활성상태)     │ 사용자 테이블 (JIT 생성, 출처=GATEWAY)
├─ L2 플랫폼관리자 · 서비스 노출(allow)          │
├─ L3 서비스별 역할 {시스템id: 역할}             │
└────────── 위임 (헤더 or API) ──────────────→  └─ L4 세밀 인가 = 사번 키로 자치
```

- **"가입"은 없다.** 계정은 관리자의 인사정보 반입(개별 또는 CSV `사번,이름,임시비밀번호`)
  → 본인 최초 로그인 + 비밀번호 변경 강제로 활성화된다.
- **역할(L3)의 원천은 게이트웨이, 의미 해석은 편입 시스템**이다. 역할명은 대문자 식별자이고
  "ADMIN 이면 무엇을 할 수 있는가"는 시스템이 정한다.
- **신뢰는 단방향(하향)** 이다. 제품 로그인은 게이트웨이 세션을 만들지 않는다.

### 1.6 운영 제약 (연동 설계에 영향)

- **역할·관리자 변경은 재로그인 후 반영**된다 (JWT 클레임 기반).
- OTP 는 `OTP_MODE`(off/admin/all) 현장 설정이며 **새 기기 로그인 시에만** 요구한다.
  ±1 스텝(90초)만 허용하므로 **서버 NTP 동기화가 필수**다.
- 시크릿은 환경변수로만 관리한다 (소스·로그 금지).

## 2. 연동 유형 판정 — 제품 · 엔진 · 파이프라인

**계약 구현에 착수하기 전에 유형부터 정한다.** 유형이 곧 작업 범위이며,
잘못 잡으면 만들 필요 없는 화면·인증을 만들거나 중복 메뉴가 생긴다.

| | **제품** | **엔진** | **파이프라인** |
|---|---|---|---|
| 정의 | 자기 도메인 데이터와 권한(L4)을 소유 | 입력을 받아 결과를 내는 처리기 | 데이터를 공급·수집하는 배치 |
| 사용자 접점 | 서비스 카드 (메뉴 노출) | 없음 — 포털 화면 뒤 | 없음, 또는 관리자 전용 화면 |
| 편입 방식 | 경로 프록시 + SSO | 브릿지 conf (메뉴 비노출) | 투입 API + (선택) 관리 카드 |
| 신원 수신 | **필수** (3.1 / 3.2) | 불필요 — 게이트웨이가 게이트 담당 | 서버-to-서버 시크릿 |
| 화면 | API 우선, 자체 UI 는 폴백 | 없음 | 관리 화면만 |
| 판정 질문 | 자기 데이터·권한을 갖는가? | 상태 없이 호출당 처리인가? | 산출물이 기존 평면(문서함 등)에 들어가는가? |

**판별 기준은 하나다 — 자기 도메인 데이터와 권한(L4)을 갖고 있는가.**
갖고 있으면 제품, 없으면 엔진이나 파이프라인이다.
1.4 절의 기능과 겹치면서 자기 데이터가 없다면, 그것은 제품이 아니라 엔진이다.

> 유형 판정 전에는 서비스 등록을 진행하지 않는다. 중복 카드는 되돌리기 어렵다.

## 3. 연동 계약 (공통 — 구현 대상)

### 3.1 경로 A — SSO 헤더 (기본 경로)

게이트웨이가 인증을 강제하고, 통과한 요청에만 신원 헤더를 붙여 업스트림으로 전달한다.

| 헤더 | 내용 |
|---|---|
| `X-Clever-Gw-Secret` | 공유 시크릿 — **검증 통과가 신뢰의 전부** (고정시간 비교 필수) |
| `X-Clever-User` | 사번 |
| `X-Clever-Name` | 이름 — **percent 인코딩** (URL 디코딩으로 복원) |
| `X-Clever-Admin` | `"1"` = 플랫폼 슈퍼관리자, `"0"` = 아님 |
| `X-Clever-Roles` | `시스템id=역할;시스템id=역할` — **자기 id 값만 읽고 나머지는 무시** |
| `X-Clever-Unit` | 부서 — percent 인코딩 (이름과 동일 규약) |

수신 규칙:

1. **시크릿 검증** → 실패면 즉시 거부 (헤더를 절대 먼저 믿지 않는다)
2. 자체 세션 수립 — 기존 세션과 **사번이 다르면 기존 세션 폐기**
3. 미등록 사번은 **JIT 생성** (출처=GATEWAY, 비밀번호 컬럼 NULL)
4. 관리자 판정 = `Admin=="1" OR roles[자기id]=="ADMIN"`
5. 역할은 **저장하지 않고 요청마다 헤더 기준** (캐시했다면 헤더로 덮어씀), **모르는 역할명 = 무권한**

**재방문 검증의 경계**: 등록된 사번이 다시 오면 **신원·상태만 검증**한다(행 존재·사용여부·세션).
**인증(비밀번호) 재검증은 영원히 게이트웨이 몫** — GATEWAY 행에 비밀번호가 없는 이유다.

> 비-SSO 서비스에는 게이트웨이가 이 헤더들을 **빈 값으로 강제**한다 — 외부에서 위조해
> 밀어 넣을 수 없다. 참조 구현: 회의록 `GatewaySsoFilter.java`.

### 3.2 경로 B — 위임 로그인 (자체 화면·단독 오리진용)

자기 로그인 폼을 유지하되 **검증만 게이트웨이에 위임**한다.

```
POST {게이트웨이}/auth/api/delegated-login     헤더: X-Clever-Gw-Secret
{ "empNo": "E1001", "password": "…", "otp": "123456"(선택), "service": "자기시스템id" }
```

| 응답 | 의미 |
|---|---|
| `200 {ok, empNo, name, isAdmin, roles, unit}` | 이 신원으로 자체 세션 수립 (JIT 규칙 동일). `unit` 은 원문(인코딩 없음) |
| `200 {otpRequired: true}` | 6자리 코드를 받아 `otp` 를 넣어 재호출 |
| `401` / `429` | 자격 불일치 / 시도 횟수 초과 |
| `403 {mustChange}` / `403 {otpEnroll}` | "포털에서 먼저 로그인하세요" **안내만 표시** (비밀번호 설정·OTP 등록 UX 는 제품에 열지 않는다) |

**비밀번호·OTP 코드는 통과만 — 저장·로깅 금지.** `service` 필드는 이용 통계 집계에 쓰인다.

### 3.3 서브패스 서빙 표준

경로 편입 대상은 **`/시스템id/` 아래에서 동작**해야 한다.

- 게이트웨이 검증 규칙 (그대로 강제된다):
  - 경로: `/영소문자-숫자-하이픈/` — **단일 세그먼트만** (예: `/meeting/`)
  - 업스트림: `http(s)://호스트[:포트]` (경로 없이)
- **프리픽스 전달 방식 2가지** — 여기서 선택이 갈린다:

| 방식 | 업스트림 표기 | 시스템이 받는 경로 | 적합 대상 |
|---|---|---|---|
| 프리픽스 유지 (**화면 제공 시 권장**) | `http://host:PORT` | `/myapp/api/x` 그대로 | 회의록 사례. 프론트 `base` 를 `/myapp/` 으로 설정 |
| 프리픽스 제거 | `http://host:PORT/` (끝 `/`) | `/x` | **순수 API 브릿지 전용** |

> ⚠️ 화면을 내려주는 시스템이 "프리픽스 제거"를 쓰면 절대경로 리소스가 전부 깨진다.
> SPA 라우팅은 **hash 라우팅**을 권장한다 (포털·회의록 모두 이 선택 — nginx 폴백 설정 불필요).

**프록시 공통 성질** (자동 생성 블록에 포함 — 별도 요청 불필요):
SSE 무버퍼링(`proxy_buffering off`) · WebSocket Upgrade 승격 · `client_max_body_size 500m` ·
`proxy_read_timeout 3600s` · `Origin` 제거(교차 출처 오인 방지).
→ **스트리밍 응답과 장시간 작업은 그대로 통과한다.**

### 3.4 시스템 간 서버-to-서버 호출

호출자는 `X-Clever-Gw-Secret` + **사번만** 전달한다.
**권한 판정은 수신 시스템이 자기 데이터로 스스로** 한다 —
호출자가 권한 주체 목록을 조립해 보내는 방식은 **금지**다(권한 계산이 시스템 밖으로 새는 구멍).

### 3.5 이용 통계 푸시

```
POST {게이트웨이}/stats/ingest      헤더: X-Clever-Gw-Secret
{ "service":"myapp", "metric":"llm_tokens_out", "amount":1280,
  "empNo":"E1001"(선택), "ts":epoch초(선택), "meta":{…}(선택) }
또는 { "events":[ …위 형식…, ] }   배치 최대 1000건
```

- `service` = services.json 의 id 규칙 (영소문자·숫자·하이픈, 32자 이내)
- `metric` = 소문자·숫자·`._-` 1~64자. 권장명: `llm_tokens_in`/`llm_tokens_out`/`llm_calls`/
  `stt_seconds`/`doc_uploaded` — 새 지표는 자유 추가
- `amount` 생략 시 1. 푸시하면 관리자 대시보드에 **즉시** 반영된다.

### 3.6 금지 사항 (계약 위반)

1. 통합 구축에서 **자체 비밀번호 보관·자체 로그인**
2. **시스템 → 타 시스템 인증 위임** (예: A 가 B 의 로그인으로 사용자를 판정)
3. 호출자가 **권한 주체 목록을 조립해 전달**
4. **시크릿 검증 없이 신원 헤더 신뢰**
5. 게이트웨이가 준 역할을 **영구 저장**하고 헤더를 무시

## 4. 등록 절차 (게이트웨이 몫)

관리자 화면에서 서비스 1건을 등록하면 nginx 프록시 조각이 자동 생성·무중단 반영된다.
**편입 시스템이 제출할 값은 굵은 항목뿐이다.**

| 필드 | 설명 |
|---|---|
| **`id`** | 영소문자·숫자·하이픈 — 역할 헤더·통계의 키가 된다 |
| **`name` / `description`** | 카드 표기 |
| **`path`** | `/id/` (경로 편입 시) |
| **`upstream`** | `http://호스트:포트` (3.3 의 끝-`/` 규약 주의) |
| **`sso`** | 계약 이행 시 ON |
| `external` | 경로 편입 대신 URL 직행(전환기) |
| `allow` | 노출 허용 사번 목록 (빈 목록 = 전원). SSO 서비스는 프록시 단에서도 403 차단 |
| `system` | 메뉴 비노출 API 브릿지 |
| `category` / `order` / `icon` | 카드 분류·정렬·아이콘(.ico) |

## 5. 유형별 추가 사항

### 5.1 제품

- 3장 계약 전부가 구현 대상이다.
- 1.4 절 기능과 겹치는 부분은 **API 로 제공하고 화면은 포털에 양보**하는 것이 표준이다.
  자체 UI 는 게이트웨이를 쓸 수 없을 때의 폴백으로만 유지한다.
- 폴백 화면의 로그인은 자체 계정이 아니라 **경로 B(위임 로그인)** 로 구현한다.

### 5.2 엔진

- 신원 수신을 구현하지 않는다. 게이트웨이가 SSO 게이트를 담당하고, 인증된 요청만 넘긴다.
- 브릿지 nginx 조각은 **수동 관리**이며 시크릿·API 키를 포함하므로 git 에서 제외한다.
  **키는 서버측에서 주입**하고 브라우저로 내려보내지 않는다.
- 합의할 것은 API 규격뿐이다 — 요청·응답 형식, 스트리밍 여부, 타임아웃, 동시 호출 상한.

### 5.3 파이프라인

- 산출물이 **문서**라면 문서함에 투입하는 것이 표준 경로다. 투입되면 기존 파싱·인덱싱·검색과
  업무 자동화의 `upload` 트리거(보고서·심사·사이클 자동 실행)가 **추가 개발 없이** 동작한다.
- **현재 공백**: 문서함 업로드 API 는 포털 세션 쿠키 인증 전용이며 폴더 권한을 세션 주체로
  판정한다. 즉 **외부 시스템의 서버-to-서버 투입 창구가 아직 없다.**
  시크릿 기반 투입 엔드포인트(투입 주체 사번 지정 포함)는 **게이트웨이 쪽 신설 작업**이므로,
  요건(형식·건수·주기)을 제출하면 설계한다.
- **권한 원칙**: 파이프라인은 **"누가 이 데이터를 볼 수 있는지"를 판정하지 않는다.**
  출처·분류 같은 **사실만 태그로 전달**하고, 열람 권한은 데이터를 보관하는 쪽이 사번 키로 판정한다.
- **망 제약**: 폐쇄망 전제이므로 외부 인터넷 접근이 필요하면 아웃바운드 경로·망 정책은
  게이트웨이 밖의 별도 합의 사항이다.

## 6. 연동 신청 양식

편입을 요청할 때 아래 항목을 채워 제출한다. 1·2번에서 걸리면 편입이 아니라 재구축 논의가 된다.

| # | 항목 | 기입 |
|---|---|---|
| 1 | 자체 계정·로그인 체계가 있는가 (사용자 테이블·비밀번호 보관 여부) | |
| 2 | 권한 판정을 **사번 키**로 자치할 수 있는가 / 현재 권한의 키는 무엇인가 | |
| 3 | 프론트엔드를 **서브패스 `/id/`** 아래에서 서빙할 수 있는가 (프레임워크·base 설정) | |
| 4 | 화면 없이 **API 만** 제공하는 형태가 가능한가 | |
| 5 | 응답 형태 — 동기 / 스트리밍(SSE·WS) / 장시간 잡 | |
| 6 | 타 시스템에 **인증·권한을 묻고 있는가** | |
| 7 | 역할 구분이 필요한가 — 필요하면 **역할명 목록과 의미** | |
| 8 | 이용 통계로 낼 지표 (지표명·단위) | |
| 9 | **1.4 절 기능과 겹치는 부분**과, 겹치지 않는 차별 기능 (한 문장) | |
| 10 | 자기 도메인 데이터·권한을 소유하는가 (2장 유형 판정) | |
| 11 | 희망 `id` · 화면 유무 · 관리자 전용 여부 | |
| 12 | 데이터 공급이 있다면 — 형태·건수·주기, 수집 대상이 사내인가 외부인가 | |

## 7. 진행 순서와 수용 기준

```
신청 양식(6장) → 유형 판정(2장) → 계약 구현(3장)
              → dev 편입 검증 → 운영 반영
```

dev 편입 검증 항목 (게이트웨이·시스템 합동, 회의록 편입 때와 동일 절차):

- [ ] 포털 로그인 → 서비스 카드 → 경로 진입까지 **재로그인 없이** 관통
- [ ] 미등록 사번 첫 진입 시 JIT 생성 (출처=GATEWAY, 비밀번호 NULL)
- [ ] 시크릿 없는 직접 호출 차단 / 위조 헤더 차단 (빈 값 강제 확인)
- [ ] 역할 변경 → 재로그인 → 기능 차이 반영
- [ ] `allow` 목록 밖 사용자 403 안내
- [ ] 스트리밍·대용량 업로드·장시간 작업 정상 통과
- [ ] `/stats/ingest` 푸시 → 대시보드 반영

문의 창구: 게이트웨이 담당자.
이 문서의 변경은 게이트웨이 저장소에서 버전으로 관리한다.
