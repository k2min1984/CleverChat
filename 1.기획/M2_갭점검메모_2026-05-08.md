# M2 갭점검 메모

> 작성일: 2026-05-08  
> 목적: M2 시나리오 코드 구현 전 결정값과 M3 설계 기본값 동기화

## 1. M2 구현 전 결정 항목

| # | 항목 | 현재 갭 | 제안 기본값 |
|---|---|---|---|
| 1 | OPERATOR 시딩 | M1은 ADMIN 시딩만 있어 OPERATOR 권한 테스트와 운영자 진입 검증이 어렵다. | 운영 기본 OPERATOR 계정은 비활성 상태로 시딩하고, 초기 로그인 시 비밀번호 변경을 강제한다. |
| 2 | 관리자 접근 권한 | `SecurityConfig`가 `/admin/**`을 ADMIN 전용으로 제한한다. | `/admin/**`은 `ADMIN`, `OPERATOR` 모두 허용하고, ADMIN 전용 메뉴는 화면에서 분기한다. |
| 3 | REST CSRF/인증 실패 | `/admin/api/**` 오류가 HTML로 반환되면 AJAX 처리가 불안정하다. | 쿠키 기반 CSRF 토큰과 API 전용 JSON 401/403 응답을 적용한다. |
| 4 | 감사 로그 상세 | 현재 AOP는 `target_id`와 before/after 기록이 부족하다. | 직접 호출용 `AuditTrailRecorder`를 추가해 서비스 명령 단위로 before/after 또는 변경 건수를 남긴다. |
| 5 | 미리보기 범위 | 챗봇 위젯 재사용은 M3 미구현 상태라 M2 구현을 막을 수 있다. | M2는 서버 렌더 시뮬레이터로 구현하고, M3에서 챗봇 위젯으로 교체한다. |
| 6 | 키워드/유사어 동시성 | 일괄 저장 시 충돌 정책이 없다. | 트랜잭션 안에서 전체 삭제 후 재삽입하는 replace 방식으로 처리한다. |
| 7 | 게시 버전 재편집 | 게시 이후 수정 UX와 오류 정책이 명확하지 않다. | 게시 버전 직접 수정은 `STATE_CONFLICT`로 차단하고 "복제 후 새 초안"만 제공한다. |
| 8 | 기존 게시 버전 처리 | 새 버전 게시 시 기존 `PUBLISHED` 처리 기준이 없다. | 새 게시 성공 시 직전 `PUBLISHED` 버전은 자동 `ARCHIVED`로 전환한다. |

## 4. 사용자 확인 결과

아래 항목은 사용자 결정값으로 확정되었다. M2 구현은 아직 시작하지 않고 문서 기준만 동기화한다.

- OPERATOR 시딩: 운영 기본 계정은 비활성 상태로 생성하고 초기 로그인 시 비밀번호 변경을 강제한다.
- `users.must_change_password` 컬럼은 Flyway `V3_1__auth_must_change_password.sql`로 분리한다. V3는 시나리오 baseline만 담당한다.
- 쿠키 보안 속성: `SameSite=Lax`, `Secure=true`, `HttpOnly=true`를 기본값으로 한다. CSRF 토큰 쿠키는 JS 접근 필요로 `HttpOnly=false` 예외를 둔다.
- 프록시 헤더: `server.forward-headers-strategy=framework`를 사용하고, 운영 프로파일에서만 부팅 경고 로그를 출력한다.
- 매칭 캐시 TTL: 기본값은 300초로 한다.
- 미리보기 범위: M2 서버 렌더 시뮬레이터로 시작하고 챗봇 위젯 구현은 M3 이후로 둔다.
