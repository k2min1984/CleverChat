# CleverChat 플랫폼 연동 적용 검토

- 작성일: 2026-09-22
- 기준: [INTEGRATION_GUIDE_v1.0.md](INTEGRATION_GUIDE_v1.0.md)와 `3.개발/cleverchat` 현재 소스
- 성격: 최초 검토 시점의 현황 비교 및 개발 범위 제안. 이후 구현된 시스템 설정·헤더 SSO·저장 경로·크롤링 상세 개선은 [구현 결과](../3.개발/cleverchat/docs/RESULT-system-settings-2026-09-22.md)를 기준으로 확인한다. 아래 전체 연동 범위가 모두 구현된 것은 아니다.
- 사용자 결정 반영: 관리자 시스템 설정에서 **독립(단독) / 연계**를 선택한다. 독립은 현재 로그인, 연계는 SSO 로그인을 사용한다. 실제 게이트웨이 연결 전에는 독립으로 개발하며, 모의 신원은 별도 개발 전용 옵션으로만 둔다.
- 확인 한계: 정본인 `PERM_SPEC_v2.0.md`, 회의록 참조 구현 `GatewaySsoFilter.java`, 게이트웨이 소스는 현재 저장소에서 찾지 못했다. 역할 계약과 프록시 동작은 해당 자료를 받아 최종 확정해야 한다.

## 1. 적용 방향

**현재 기능을 유지하면서 플랫폼에 편입할 수 있다. 다만 엔드포인트나 JSON 형식만 맞추는 수준은 아니며, 인증·사용자 식별·권한·경로 처리가 주요 변경 대상이다.**

CleverChat은 시나리오·버전·대화·검색·수집 대상·수집 문서·운영 권한을 소유한다. 따라서 전체 시스템의 권장 분류는 **제품**이다. 이 안의 크롤링 결과 공급 기능은 **파이프라인 계약**을 추가로 적용한다. 이 분류 때문에 크롤러를 별도 서버나 프로젝트로 분리할 필요는 없다.

- 게이트웨이: 계정·비밀번호·OTP, 플랫폼 서비스 노출, 서비스별 역할의 원천을 담당한다.
- CleverChat: 시나리오 실행·관리, 자체 도메인 데이터, 사번 기준 세부 권한, 수집·검색 기능을 담당한다.
- 포털: 일반 사용자 화면을 제공한다. 기존 CleverChat 화면은 폴백과 관리 화면으로 활용하는 안을 협의한다.
- 독립 설치판: 기존 로컬 계정 기능을 유지할 수 있다. 통합 설치판: 게이트웨이 신원만 사용하고 로컬 비밀번호를 보관하지 않는다.
- 연계 전 개발: SSO·계정·권한 구조를 먼저 구현하고 시스템 설정은 독립으로 유지한다. SSO 이후 처리를 시험할 때만 개발 전용 모의 신원을 사용한다.

이전의 “기능이 JSON/파라미터로 송수신되면 된다”는 설명은 기능 API 연결에는 해당하지만, 이번 가이드의 **제품 편입 계약 전체를 충족하는 조건은 아니다.**

또한 “게이트웨이 코드 수정 없음”은 기존 서비스 등록·프록시·SSO 전달 기능을 사용하는 범위의 설명이다. 포털에 CleverChat 전용 기능을 표시하는 프론트엔드 연결과, 아직 없는 문서 투입 API는 별도 작업이다.

## 2. 현재 구현과 차이

| 항목 | 현재 구현 | 적용에 필요한 일 |
|---|---|---|
| 독립 기동 | Spring Boot·PostgreSQL 기반 독립 실행 | 유지. 게이트웨이와 DB 또는 소스 코드를 공유할 필요 없음 |
| 제품 API | `/chat/api/**`, `/admin/api/**`에 업무 API 존재 | 게이트웨이 신원·권한 적용, 포털용 계약 문서화, 누락 API 보강 |
| 외부 전용 API | `/external/api/v1/status`만 제공. Bearer 또는 `X-CleverChat-Api-Key` 검증 | `X-Clever-Gw-Secret` 기반 계약은 별도 구현 필요. 기존 상태 API를 업무 연동 완료로 간주하면 안 됨 |
| 관리자 인증 | `LoginController`가 로컬 `password_hash`를 검증하고 `AdminSession` 생성 | SSO 헤더 수신, JIT 사용자 생성, 통합 모드 로컬 로그인 차단 |
| 사용자 모델 | `tb_user.user_no`, `username`, 필수 `password_hash`; 역할은 `tb_user_role` | 사번·출처·부서 식별 추가, GATEWAY 사용자 비밀번호 NULL 허용 및 강제 |
| 역할·메뉴 | `ADMIN/OPERATOR/USER`, `RoleGuard`, 역할별 메뉴 매핑 | 게이트웨이 역할을 요청마다 해석. L3 역할의 DB 영구 저장 금지. 데이터별 L4 규칙 별도 정의 |
| 채팅 사용자 | `anonymous_id` 쿠키가 대화 소유권·이력 조회 기준 | 통합 모드는 사번→내부 사용자 번호로 소유권 판정. 익명 쿠키만으로 다른 계정의 대화를 이어받으면 안 됨 |
| 서브패스 | Thymeleaf `@{...}`와 `ADM.url()` 일부 대응. JS에 `/chat/api/...`, `/admin/api/...` 절대경로 존재 | `/cleverchat/` 컨텍스트 설정, JS·응답 링크·쿠키·리다이렉트 전수 점검 |
| 크롤링 | 작업 큐, 상태 조회, DB 저장, 선택한 서버 경로에 JSON 스냅샷 저장 | 문서함 투입 클라이언트·전송 이력·재전송 추가. 로컬 JSON 저장만으로 문서함 연동되지 않음 |
| 통계 | 자체 로그·통계·감사 기능 | 게이트웨이 `/stats/ingest` 전송 어댑터 필요 |
| AI 모델 호출 | `AiAnswerProvider`와 `NoopAiAnswerProvider`, 답변 제안 기능 플래그 | 현재 실제 vLLM HTTP 호출 구현 없음. 모델 호출을 CleverChat이 담당할 때 별도 구현 |
| 온톨로지 | 해당 외부 시스템을 호출하는 구현을 찾지 못함 | 이번 문서는 플랫폼 편입 표준이며, 온톨로지 조회·개체·관계 규격은 별도 필요 |

## 3. 필수 변경: 인증·사용자·권한

### 3.1 설치 모드와 계정 전환

관리자 **시스템 설정 > 운영 방식**에 `독립(단독)`과 `연계` 두 가지를 제공한다. 내부 값은 각각 `LOCAL`, `GATEWAY`로 제안한다. **새로 추가할 설정**이며 현재 구현된 옵션은 아니다. 신규 설치 및 현재 개발 환경의 기본값은 기존 동작을 유지하는 독립이다.

- `LOCAL`(독립): 기존 자체 로그인과 로컬 계정을 사용한다. 게이트웨이 주소나 시크릿이 없어도 기동하고 업무 기능을 사용할 수 있다.
- `GATEWAY`(연계): 게이트웨이 SSO 또는 위임 로그인만 허용한다. 로컬 비밀번호 인증, 초기 계정 시딩, 자체 비밀번호 설정 기능을 차단한다.
- 모의 신원은 세 번째 운영 방식으로 표시하지 않는다. 별도 개발·자동화 테스트 옵션으로만 사용한다.
- 통합 환경에 기존 로컬 계정이 있으면, 사번 매핑·기존 데이터 소유자·감사 이력을 확인한 뒤 전환한다. 비밀번호 해시를 남겨 두고 로그인 버튼만 숨기는 방식은 가이드 미충족이다.
- 운영 DB 전환은 별도 마이그레이션 절차로 수행한다. 분석 단계에서 기존 계정이나 데이터를 삭제하지 않는다.

DB 변경 제안:

| 대상 | 변경안 |
|---|---|
| `tb_user` | `auth_source`(`LOCAL/GATEWAY`), `emp_no`, `unit` 추가. 길이·사번 유일성은 정본 확인 후 결정 |
| `password_hash` | NULL 허용으로 변경하되 GATEWAY 행은 반드시 NULL, LOCAL 행은 비밀번호 필수 제약 적용 |
| 사용자 식별 | 외부 식별자는 사번. 내부 PK `user_no`와 기존 FK는 유지하여 변경 범위를 줄임 |
| `username` | 기존 로컬 ID와 외부 사번의 충돌 처리·JIT 조회 규칙 결정. 우연히 문자열이 같다고 자동 계정 병합하지 않음 |
| `tb_user_role` | 로컬 설치판의 역할 저장에는 유지 가능. 게이트웨이 L3 역할을 복사해 영구 저장하지 않음 |
| 도메인 권한 | 사번에 연결된 내부 사용자 기준 소유자·관리 범위 정의. 필요 시 제품 자체 ACL 추가 |

`frst_regr_empno` 같은 컬럼명이 일부 존재해도 전체 권한이 사번 기반으로 구현됐다는 의미는 아니다. 현재 로그인·채팅·권한 경로를 함께 바꿔야 한다.

### 3.1.1 시스템 설정 화면과 적용 방식

현재 관리 기능에는 공통 코드·메뉴·권한 관리가 있다. 운영 방식 전환을 위한 설정 화면·저장 구조·조회 API·변경 API는 추가 구현한다.

| 화면 항목 | 동작 |
|---|---|
| 운영 방식 | 독립(단독) / 연계 선택. 현재 적용값과 편집 중인 값을 구분 |
| 게이트웨이 주소 | 연계용 포털 이동 및 위임 로그인에 사용할 주소 |
| 서비스 ID | 역할 헤더와 통계의 키. `cleverchat` 제안 |
| 시크릿 설정 상태 | 서버 환경변수에 설정되어 있는지만 표시. 값 입력·조회·DB 저장은 제공하지 않음 |
| 연계 로그인 확인 | 실제 게이트웨이를 통해 시험 로그인하고 설정된 서비스 신원이 수신되는지 확인. 별도 미정 API를 가정하지 않음 |
| 저장·적용 | 필수 설정 검사 후 운영 방식 적용, 변경 이력 기록, 새 로그인 안내 |

로그인 처리:

```text
시스템 설정의 운영 방식 조회
  ├─ 독립 → 현재 로그인 화면 → 로컬 계정 검증 ───────┐
  └─ 연계 → 검증된 SSO 신원 → GATEWAY 사용자 JIT ──┤
             └─ 직접 진입: 포털 로그인 안내/이동     │
                또는 합의된 위임 로그인             ↓
                                         공통 세션·권한·업무 기능
```

적용 규칙:

1. 설정은 DB에 저장해 재기동 후에도 유지한다. 런타임 인증 분기에서 현재 설정을 읽어 로그인 방식과 요청 검증을 함께 바꾼다. 화면만 전환하거나 시작 시 생성한 Bean만으로 모드를 고정하지 않는다.
2. ADMIN 권한으로만 변경하며 기존 CSRF 검사와 감사 로그를 적용한다. URL 파라미터나 쿠키로 개별 사용자가 독립 모드를 강제할 수 없다.
3. 변경 적용 시 설정 버전을 올리고 기존 세션은 다음 요청부터 재로그인하도록 한다. 여러 서버로 운영한다면 같은 버전을 사용해 서로 다른 인증 방식이 동시에 적용되지 않도록 한다.
4. 연계 준비 중에는 설정을 작성·보관하더라도 현재 독립 로그인은 유지한다. 실제 연계 모드 적용은 설정 검증과 연계 로그인 확인 후 수행한다.
5. 연계 모드의 SSO 실패나 게이트웨이 장애를 이유로 로컬 계정 또는 모의 관리자에게 자동 전환하지 않는다. 복구는 서버 운영자가 설정과 게이트웨이 연결을 점검하는 별도 절차로 둔다.
6. 로그인 모드 전환과 사용자 데이터 전환은 구분한다. 버튼 저장만으로 기존 비밀번호를 삭제하지 않는다. 통합 운영 전환 시 사번 매핑과 LOCAL 계정 정리를 별도 수행해 가이드의 비밀번호 미보관 조건을 충족한다.
7. GATEWAY 사용자는 로컬 비밀번호가 없으므로 독립으로 되돌리는 설정만으로 로컬 로그인 계정이 생기지 않는다. 독립 재구축/복구 시 필요한 로컬 계정 확보를 별도로 확인한다.
8. `/cleverchat/` 컨텍스트와 프록시 배포 경로는 로그인 모드와 별도 설정이다. 인증 모드 저장이 서버 컨텍스트까지 즉시 변경한다고 가정하지 않는다.

### 3.1.2 개발 전용 모의 신원

기존 기능 개발은 **시스템 설정을 독립으로 유지**하면 된다. 실제 게이트웨이 없이 SSO 이후의 JIT·세션·권한을 검증해야 할 때만 모의 신원을 사용한다.

- 모의 신원은 일반 시스템 설정 선택지에서 제외한다. `dev/test` 프로필과 별도 명시적 테스트 설정이 모두 있어야 활성화하며, `stage/prod`에서는 기동을 거부한다.
- 개발 환경의 연계 방식에서 실제 신원 공급기 대신 모의 공급기를 주입한다. 운영 방식 검증을 포함한 실제 게이트웨이 시험을 통과했다고 처리하지 않는다.
- 서버에 미리 등록한 테스트 사번·부서·플랫폼 관리자 여부·서비스 역할을 사용한다. 사용자 입력 헤더/파라미터로 임의 관리자 권한을 부여하지 않는다.
- 실제 연계와 동일한 JIT·세션·메뉴/API 권한·데이터 소유권 로직을 호출한다. 개발 DB에 GATEWAY 출처·비밀번호 NULL로 생성하며 세션·로그·화면에는 모의 신원 사용을 표시한다.
- 다른 테스트 사번으로 변경하거나 모의 신원 사용을 끄면 이전 세션을 재사용하지 않는다. 테스트 계정은 운영으로 이관하지 않는다.
- 시크릿 검증·percent 디코딩은 유효/위조 헤더 자동화 테스트로 별도 검증하고, nginx·allow·OTP·위임 로그인은 실제 연계 시 최종 확인한다.

### 3.2 경로 A: 게이트웨이 SSO 수신

신규 `GatewaySsoFilter`와 신원 해석 서비스 등을 두어 기존 인증 인터셉터보다 앞에서 처리한다.

1. `X-Clever-Gw-Secret`을 환경변수의 시크릿과 고정시간 비교한다. 실패하면 신원 헤더를 사용하지 않고 거부한다.
2. `X-Clever-User`로 사번을 식별하고 이름·부서는 가이드의 percent 인코딩 규칙에 맞춰 복원한다.
3. 미등록 사번은 `auth_source=GATEWAY`, `password_hash=NULL`로 JIT 생성한다. 동시 첫 접속에도 중복 행이 생기지 않도록 제약·트랜잭션을 둔다.
4. 기존 세션의 사번과 다르면 세션을 폐기하고 새로 만든다. 같은 사번이어도 비활성 사용자 상태를 확인한다.
5. `X-Clever-Roles`에서 **자기 서비스 ID의 항목만** 해석하고 세션/요청의 유효 역할을 갱신한다. 이전 세션의 관리자 권한을 계속 쓰지 않는다.
6. 관리자 판정은 가이드대로 `X-Clever-Admin=1` 또는 자기 서비스 역할 `ADMIN`이다. 알 수 없는 역할에는 권한을 주지 않는다.
7. 관리 API뿐 아니라 통합 모드 채팅·이력·문서 상세 접근에도 검증 범위를 적용한다. 직접 업스트림 호출 시 기존 세션 쿠키만으로 검증을 우회하지 못하게 한다.

`AdminSession`에는 사용자 출처·사번·필요한 부서 정보를 표현할 수 있어야 한다. 일반 사용자 신원도 표현하는 공통 주체 모델로 확장하거나 분리한다. 기존 인터셉터·MyBatis 구조를 활용할 수 있으므로 Spring Security/JPA로의 전면 전환은 필수가 아니다.

### 3.3 경로 B: 폴백 화면 위임 로그인

제품 유형의 폴백 화면을 유지하면 이 경로도 구현 대상이다.

- CleverChat 서버가 게이트웨이 `/auth/api/delegated-login`을 호출하고 성공 신원으로 자체 세션을 만든다.
- `otpRequired=true`를 일반 로그인 성공으로 처리하지 않는다. OTP 재입력 흐름을 제공한다.
- `401/429`, `mustChange`, `otpEnroll`을 구분한다. 비밀번호 변경·OTP 등록은 포털로 안내한다.
- 사용자 비밀번호와 OTP는 저장하거나 로그에 남기지 않는다. 요청/응답 디버그 로깅에도 포함하지 않는다.
- 위임 로그인 세션의 만료·역할 갱신·사용자 비활성화 반영 방식은 가이드에 상세 규칙이 부족하므로 추가 합의가 필요하다.
- 헤더 SSO 경로와 위임 로그인 경로의 허용 범위를 명시한다. 모든 요청에 SSO 헤더를 강제해 폴백까지 막거나, 폴백 세션을 이유로 SSO 경로 검증을 생략하면 안 된다.

### 3.4 역할과 데이터 권한

권장 역할 해석 초안은 다음과 같다. 실제 등록 역할은 `PERM_SPEC_v2.0.md` 확인 후 확정한다.

| 역할 | CleverChat 내부 의미 제안 |
|---|---|
| `ADMIN` | 제품 관리 및 설정. 기존 OPERATOR 기능 포함 |
| `OPERATOR` | 시나리오 운영·크롤링 실행·실행 이력 검토 등 허용된 운영 업무 |
| `USER` | 일반 채팅·허용된 시나리오·문서 조회, 자기 대화 이력 |
| 그 밖의 역할 / 역할 없음 | 기본 거부. 플랫폼 슈퍼관리자 규칙은 가이드에 따라 별도 적용 |

- 화면 메뉴 숨김과 API 인가는 별개다. 조회·변경 API마다 허용 역할과 데이터 범위를 명시해야 한다.
- 현재 익명 대화는 통합 사용자에게 자동 귀속시키지 않는다. `ChatRequestContext`, 세션 생성, 소유자 검사, 이력 SQL을 함께 수정한다.
- 채팅 이력·피드백·문서 본문·검색 결과에 동일한 주체 기준을 적용한다. 검색에서 제외한 문서를 상세 URL로 우회 조회하지 못해야 한다.
- 내부 직원별/부서별 문서 범위가 필요한지 확정한다. 공개 크롤링 문서는 공용이라는 정책도 가능하지만, 사내 문서까지 같은 정책으로 자동 확대하지 않는다.

### 3.5 서버 간 호출

- 기존 `X-CleverChat-Api-Key` 인증과 가이드의 `X-Clever-Gw-Secret` 계약은 서로 다르다.
- 서버 간 업무 API는 시크릿과 사번으로 호출 주체를 식별하고, 수신 측의 L4 데이터로 인가한다.
- 호출자가 보낸 역할·권한 대상 목록을 신뢰하지 않는다. SSO용 역할 헤더 처리와 서버 간 API 처리를 구분한다.
- 공유 시크릿의 배포 범위와 게이트웨이/다른 시스템의 요청 구분 방식, 역할 헤더 없는 서버 간 호출에서의 L4 권한 규칙은 게이트웨이 팀과 명확히 해야 한다.

## 4. 서브패스와 포털 API

### 4.1 `/cleverchat/` 서빙

권장 서비스 ID는 `cleverchat`이며 확정값은 아니다. 자체 화면도 제공한다면 프리픽스 유지 방식으로 등록한다.

| 항목 | 제안 |
|---|---|
| 서비스 ID / 경로 | `cleverchat` / `/cleverchat/` |
| 업스트림 | `http://<CleverChat 호스트>:8080` — 끝 `/` 없음 |
| 애플리케이션 | `SERVER_SERVLET_CONTEXT_PATH=/cleverchat` 설정 후 화면·API 검증 |
| 자체 DB | 기존 PostgreSQL 유지 |
| 관리 화면 | 포털에서 필요한 관리자에게만 노출. 등록 방식은 협의 |

필요 작업:

- `chat.js` 등의 루트 절대경로를 공통 base URL 생성기로 교체한다. 이미 있는 `ADM.url()`과 Thymeleaf 컨텍스트 처리부터 재사용한다.
- API 응답이 만드는 문서 링크, 로그인/로그아웃 이동, 다운로드·폼 action·정적 자원 경로도 확인한다.
- `anonymous_id`의 현재 `Path=/`와 제품 세션 쿠키 이름·Path를 점검해 다른 제품 쿠키와 충돌하지 않도록 한다. 독립판과 통합판을 모두 검증한다.
- 게이트웨이의 프록시 헤더와 `forward-headers-strategy`, 관리자 IP 허용 정책을 함께 검증한다. IP 필터를 끄는 방식으로 해결하지 않는다.
- 현재 Thymeleaf 방식은 그대로 사용 가능하다. 가이드의 hash 라우팅 권고 때문에 Vue/SPA로 재작성할 필요는 없다.
- API 전용으로 프리픽스를 제거하는 안을 선택한다면 그 배포의 실제 수신 경로를 별도 합의한다. 같은 업스트림을 유지/제거 방식에 무조건 혼용하지 않는다.
- iframe 임베딩은 가이드의 필수 조건이 아니다. 필요하다고 합의한 경우에만 현재 `X-Frame-Options: DENY`, `frame-ancestors 'none'` 정책을 검토한다.

### 4.2 재사용할 API와 추가 계약

| 업무 | 기존 진입점 예 | 포털 연동 시 보강 |
|---|---|---|
| 시나리오 기반 채팅 | `/chat/api/sessions`, `/sessions/auto`, 선택·자유 입력·뒤로가기 | 인증 주체 바인딩, 응답 DTO·대화 상태 계약 |
| 대화 이력·피드백 | `/chat/api/history`, 세션 이력, 메시지 피드백 | 사번 기준 소유권·기기 간 이력 일관성 |
| 시나리오 관리 | `/admin/api/scenarios`, 그래프·버전·발행·활성화 | 역할별 API 인가와 포털 편집 화면 연결 |
| 크롤링 | `/admin/api/crawl-targets/{id}/run`, `/crawl-jobs`, `/crawl-runs`, `/crawl-documents` | 요청 접수와 완료를 구분, 작업 ID 기반 조회, 필요 시 페이지네이션·진행 정보 보강 |
| 검색 | 채팅의 검색 흐름, 관리자 `/admin/api/search/test` | 독립된 일반 사용자 검색 API가 필요하면 추가. 관리자 시험 API를 그대로 일반 공개하지 않음 |
| 외부 API 상태 | `/external/api/v1/status` | 기존 상태 확인 기능 유지 또는 연동 상태 항목 보강 |

표의 축약 경로는 같은 컨트롤러의 기본 경로를 따른다. 모든 경로에 `/cleverchat` 배포 컨텍스트가 추가될 수 있다.

- 현재 공통 응답은 `{success, data, error}`이다. 가이드가 모든 제품 응답을 `{ok,...}`로 강제하는 것은 아니므로 전면 변경 대신 포털과 계약하면 된다.
- API 명세에는 버전, 요청·응답 예시, 오류 코드, 권한, 타임아웃, 작업 상태, 재요청·중복 처리 규칙을 포함한다.
- 관리 POST는 현재 CSRF 토큰과 폼 ID를 검증하고 매번 재발급한다. 포털의 최초 토큰 발급과 동시 요청 처리 계약이 필요하다. PUT/DELETE 등 변경 요청의 보호 범위도 함께 정리한다.
- 브라우저 요청과 서버 간 요청의 CSRF 적용 방식을 구분한다. 서버 간 전용 API 예외를 추가하더라도 시크릿·주체·인가 검증을 전제로 한다.
- 단일 오리진 경로 연동에는 무분별한 CORS 허용이 필요 없다.
- 현재 API는 동기 JSON 응답과 크롤링 비동기 작업 조회 방식이다. SSE/WS 응답 구현은 없다. 가이드의 프록시 스트리밍 지원만으로 제품 스트리밍 기능이 생기지는 않는다.

## 5. 크롤링 결과 공급

### 5.1 현재 JSON 기능의 재사용 범위

현재 JSON 스냅샷에는 `schemaVersion`, `crawledAt`, `targetId`, `targetLabel`, `documentId`, `url`, `title`, `content`, `contentHash`, `httpStatus`가 들어간다. 이 데이터는 외부 투입용 변환의 재료로 재사용할 수 있다.

다만 서버 디스크에 JSON이 생성되는 것과 게이트웨이 문서함에 등록되는 것은 별개다. 수신 시스템이 그 파일 경로를 읽을 수 있다고 가정하지 않는다.

### 5.2 양쪽 작업

| 담당 | 작업 |
|---|---|
| 게이트웨이 | 가이드 5.3의 서버 간 문서 투입 API 신설. 공유 시크릿·투입 사번 검증, 대상 폴더 권한 판정, 파싱·인덱싱 접수/결과 규격 제공 |
| CleverChat | 수집 완료 문서 변환·전송, 투입 주체 사번·목적지 설정, 전송 이력·오류·재시도 관리 |
| 공동 | 허용 문서 형식/JSON 수용 여부, 파일/본문 전송 방법, 최대 크기·건수·주기, 중복 키, 수정·삭제 반영, 상태 조회 방식 합의 |
| 현장 인프라 | 외부 인터넷 수집이 필요한 경우 아웃바운드 경로·프록시·인증서·망 정책 승인 |

전송 실패가 수집 성공을 지우지 않도록 수집 상태와 전송 상태를 분리하는 안을 권장한다. 전송 대기 테이블(outbox)에 문서 버전·목적지·시도 횟수·결과를 기록하고 재시도한다. 이는 신규 기능이다.

출처 URL·수집 시각·분류 등 사실만 전달하고, “열람 가능한 사번 목록”을 크롤러가 계산해 보내지 않는다. 열람 권한은 문서함이 판단한다. 중복 투입 방지는 양쪽이 합의한 키로 구현하며, 현재 가이드만으로 수신 측 중복 방지가 보장된다고 볼 수 없다.

## 6. 통계·AI·온톨로지

### 6.1 통계 푸시

제품 편입의 수용 기준에 `/stats/ingest` 반영이 포함되므로 구현 범위에 넣는다.

- 우선 후보: `chat_sessions`, `chat_messages`, `search_calls`, `crawl_documents`, `crawl_failures`. 이름·단위·집계 시점은 합의한다.
- 모델 호출을 실제 구현한 뒤 `llm_calls`, `llm_tokens_in`, `llm_tokens_out`을 추가한다. 현재 없는 토큰 사용량을 추정해 실제 계측처럼 전송하지 않는다.
- 서버에서 시크릿을 주입하고 비동기 배치로 보낸다. 사용자 응답을 통계 수신 장애에 묶지 않는다.
- 배치 최대 1000건을 지키고 재전송 중복 집계 정책을 합의한다. 문서에 이벤트 멱등성 계약은 명시되지 않았다.
- 게이트웨이 접속 통계와 CleverChat 기능 통계의 집계 책임을 나눠 이중 집계를 피한다.

### 6.2 vLLM과 온톨로지

이번 가이드만으로 두 연동을 구현할 수는 없다.

- vLLM: 현재 실제 구현은 `NoopAiAnswerProvider`뿐이다. CleverChat이 생성까지 수행할지, 포털이 LLM을 호출하고 CleverChat은 시나리오/근거만 반환할지 먼저 정한다. 전자라면 endpoint·모델·인증·요청/응답·타임아웃·스트리밍·오류 계약과 실제 Provider 구현이 필요하다.
- 온톨로지: 외부 시스템의 endpoint, 인증, 개체 식별자, 관계/속성 스키마, 조회 질의와 응답, 출처·버전·증분 동기화 규칙이 별도로 필요하다.
- 플랫폼 편입을 위한 SSO와 온톨로지 의미·데이터 연동을 같은 완료 항목으로 묶지 않는다.

| 2 | SSO A, 역할 갱신, 사용자별 데이터 권한 | CleverChat. MOCK와 자동화 헤더 시험으로 선행 개발 | 모의 사번 변경·권한별 허용/거부 확인. 실제 연계 시 재로그인 없는 진입 확인 |
| 3 | `/cleverchat/` 경로·쿠키·기존 API 보강 | CleverChat + 프록시 설정은 게이트웨이 | 화면·정적 파일·JSON API·리다이렉트 정상 |
| 4 | 폴백 위임 로그인 B, 포털 기능 연결 | CleverChat + 포털 팀 | OTP/계정 상태 흐름과 기존 업무 기능 검증 |
| 5 | 통계 푸시·운영 설정·합동 수용 시험 | 양 팀 | 가이드 7장과 아래 시험 통과 |
| 병행/추가 | 문서함 공급 | 게이트웨이 투입 API 계약 선행 | 수집→투입→인덱싱→권한별 검색 확인 |
| 별도 범위 | 실제 vLLM 호출·온톨로지 연동 | 각 외부 시스템 API 계약 선행 | 개별 데이터/호출 계약 시험 통과 |

1~5가 제품 편입의 기본 작업이다. 실제 연계가 준비될 때까지 1~3과 각 기능의 모의/자동화 시험을 먼저 진행할 수 있다. 위임 로그인 클라이언트도 모의 응답으로 개발하되, 실제 포털 접속·OTP·프록시·통계 수신 시험 완료와 구분한다. 문서함 공급과 모델·온톨로지 연동은 선택한 업무 범위에 따라 추가한다. 코드 재작성보다 경계 계층과 사용자 식별 변경이 중심이지만, 채팅 소유권 변경은 기존 데이터와 회귀 시험까지 포함해야 한다.

## 9. 먼저 확인할 사항

1. `PERM_SPEC_v2.0.md`와 회의록 SSO 참조 소스 제공. 특히 알려진 역할 목록·사번 형식·사용 중지 처리 확인.
2. 제품/브릿지 서비스 ID: `cleverchat`과 `cleverchat-api`를 따로 쓰면 어느 ID의 역할을 수신하는지. 임의로 둘 다 신뢰하지 않음.
3. 포털에서 직접 제공할 CleverChat 기능 범위와 자체 관리 화면을 여는 방식. 서비스 카드 중복 여부.
4. 위임 로그인 응답의 정확한 roles 구조, OTP 도전 상태, 세션 TTL·역할 재검증·로그아웃/계정 비활성화 반영 규칙.
5. 서버 간 API가 사용할 사번·L4 권한 데이터와 공유 시크릿 배포/교체 범위. SSO 요청과 서버 간 요청의 구분.
6. 문서 투입 API의 제공 일정과 형식·폴더 지정·중복/수정/삭제 처리·결과 조회 계약. 현 가이드에는 해당 API가 없다고 명시됨.
7. 단일 오리진의 실제 HTTP/HTTPS, 쿠키와 프록시 헤더 정책, 폐쇄망 외부 수집 경로.
8. vLLM 호출 책임 및 온톨로지 시스템 별도 API 문서. 현재 통합 가이드는 이를 정의하지 않음.

## 10. 수용 시험

- 시스템 설정의 독립 선택 시 기존 로그인·업무 정상 동작, 설정 재기동 유지. 연계 설정 저장 전 검증과 적용 후 재로그인 확인.
- 게이트웨이 없이 개발 전용 모의 신원으로 테스트 사용자 JIT·역할별 API 허용/거부·사번별 데이터 격리 확인.
- MOCK 권한을 외부 헤더/파라미터로 변경할 수 없음. 비활성 사용자·미등록 역할에 권한 부여되지 않음.
- stage/prod의 모의 설정 활성화 시 기동 거부. 독립↔연계 또는 실제↔모의 신원 변경 시 이전 세션 재사용 차단. 모드 변경 API의 ADMIN 권한·CSRF·감사 로그 확인.
- 포털 로그인→CleverChat API/화면 진입 시 추가 로그인 없음.
- 미등록 사번 동시 첫 접속 시 JIT 계정 1개, GATEWAY 출처, 비밀번호 NULL.
- 시크릿 누락/위조, 다른 서비스 역할만 존재, 알 수 없는 역할, 비활성 사용자 요청 거부.
- 같은 브라우저에서 사번 변경 시 세션 교체, 이전 사용자의 대화·문서·피드백 접근 차단.
- 게이트웨이 역할 변경 후 재로그인하면 기존 CleverChat 세션의 과거 권한이 남지 않음.
- allow 목록 밖 사용자 403, 서버 간 호출자가 보낸 권한 목록 무시 및 수신 측 인가 확인.
- 위임 로그인 성공/OTP/401/429/mustChange/otpEnroll 및 로그 비노출 확인.
- `/cleverchat/`에서 정적 자원·JS API·링크·폼·로그인 이동·쿠키 정상, 다른 제품 세션과 충돌 없음.
- 포털에서 채팅·시나리오·크롤링 실행과 작업 상태 조회 정상. 장시간 작업을 접수 성공과 완료 성공으로 구분.
- 구현 범위의 업로드·장시간 요청 검증. SSE/WS를 추가한 경우에만 실제 스트리밍 시험 포함.
- 통계 푸시의 대시보드 반영·실패 재시도·중복 집계 정책 확인.
- 문서 공급 범위 포함 시 투입 사번/폴더 권한·본문·메타데이터·중복·인덱싱 결과 확인.
- LOCAL 모드 기존 로그인·익명 채팅·관리 기능 회귀 확인.
