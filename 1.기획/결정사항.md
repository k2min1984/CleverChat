## 1. 채택 결과 요약

| 항목 | 선택 | 사유 |
|------|------|------|
| 빌드 도구 | **Maven** | 전자정부프레임워크 표준, 공공/온프레미스 인력 친숙도 최상 |

| 마이그레이션 | **Flyway** | 스키마 형상관리 표준, 단순·검증된 도구 |
| 커넥션 풀 | **HikariCP** | Spring Boot 기본, 성능·안정성 우수 |

| 검색 엔진 | **PostgreSQL FTS + pg_trgm** | 별도 인프라 없이 키워드/유사어/부분일치 충족 |
| HTML 파서 | **Jsoup** | 사실상 표준, 라이선스(MIT) 안전 |

| 로깅 | **Logback + JSON 패턴(운영)** | 운영 로그 수집기 친화 (Filebeat 등) |
| HTTPS | **리버스 프록시(nginx) 종단** | 공공기관 일반 패턴, 인증서 운영 일원화 |
| 빌드 산출물 | **실행 가능 JAR + systemd** | 외장 Tomcat 운영도 가능하나 단순성 우선 |
| 시크릿 관리 | **OS env + 외부 properties 파일** | 외부 KMS/Vault 미가정. `application-prod.yml`은 placeholder만 |
| CI | **Jenkinsfile 초안** | 온프레미스 표준 |
| 테스트 | **JUnit5 + Mockito + Testcontainers(PostgreSQL)** | DB 의존 통합 테스트 신뢰성 |

## 2. 명시적으로 채택하지 않은 것

| 미채택 | 사유 |
|--------|------|
| **JPA** | MyBatis와 혼용 시 트랜잭션·캐시 경계 복잡. 단순 CRUD도 MyBatis로 통일 |
| **Gradle** | 공공기관 인수·인계 시 Maven이 무난 |
| **Redis** | 단일 노드 가정. 세션·캐시는 JDBC/Caffeine로 충분 |
| **Elasticsearch** | 초기 데이터량 가정 시 PostgreSQL FTS로 충분. M4 이후 필요 시 도입 |
| **Docker(운영)** | 온프레미스 정책상 컨테이너 불가한 곳 다수. 개발환경 PostgreSQL만 Docker Compose 제공 |
| **클라우드 KMS/Vault** | 온프레미스 가정. 시크릿은 OS 환경변수 + 권한 분리된 properties 외부 파일 |

## 3. 패키지·디렉토리 규약

- 그룹: `kr.co.cleverchat`
- 모듈 구조 (도메인 중심):
  ```
  kr.co.cleverchat
  ├── CleverChatApplication
  ├── config/        (Security, Web, MyBatis, Async 등 인프라 설정)
  ├── common/        (예외, 응답 포맷, 유틸, 감사 AOP)
  ├── web/           (사이트 공통 페이지 — 홈/에러/안내)
  └── domain/
      ├── auth/      (관리자 인증·권한)
      ├── admin/     (관리자 화면 공통)
      ├── scenario/  (시나리오·노드 관리)
      ├── chatbot/   (사용자 챗봇 런타임)
      ├── search/    (검색)
      ├── crawl/     (크롤링·파싱)
      └── ops/       (공지·통계·감사 조회)
  ```
- 모듈 내 표준 하위 패키지: `controller / service / mapper / dto / model`
- MyBatis 매퍼 XML: `src/main/resources/mapper/<domain>/*.xml`
- Flyway: `src/main/resources/db/migration/V{n}__{name}.sql`

## 4. 환경 분리

| 프로파일 | 용도 | DB | 로그 | HTTPS |
|----------|------|----|----|------|
| `dev` | 로컬 개발 | Docker Compose PostgreSQL | 콘솔, DEBUG | 미사용 |
| `stage` | 검증 | 물리 PostgreSQL (검증 DB) | 파일+JSON, INFO | nginx 종단 |
| `prod` | 운영 | 물리 PostgreSQL (운영 DB) | 파일+JSON, WARN | nginx 종단 |

- 시크릿(`spring.datasource.password` 등)은 절대 `application-*.yml`에 평문 저장하지 않는다.
- 운영은 `${DB_PASSWORD}` 등 OS 환경변수 또는 `--spring.config.additional-location`으로 외부 파일 주입.

## 5. 추후 재검토 트리거

- 동시 사용자 100 이상, 또는 다중 노드 도입 → **Redis 세션·캐시**, **Quartz JDBC 스케줄러**
- 검색 결과 품질 한계, 또는 백데이터 100만건 이상 → **Elasticsearch** 도입
- AI 답변 추천 요구 확정 → **벡터 DB (pgvector)** 검토 후 RAG 구조
- 멀티테넌시 요구 → 스키마 분리 vs 컬럼 분리 재설계

## 7. M2 구현 전 기본값 결정 (2026-05-08)

| 항목 | 선택 | 사유 |
|------|------|------|
| OPERATOR 계정 | **운영 기본 계정 비활성 시딩 + 최초 로그인 비밀번호 강제 변경** | 운영 진입 계정을 제공하되 기본 비밀번호 사용과 즉시 권한 행사를 차단 |
| 관리자 접근 권한 | **`/admin/**`은 ADMIN/OPERATOR 허용** | 운영자 업무 화면 진입을 보장하고 ADMIN 전용 기능은 화면/메서드 보안으로 분리 |
| 관리자 REST 오류 | **`/admin/api/**`는 JSON 401/403 반환** | AJAX 호출에 HTML 로그인 페이지가 섞이지 않도록 공통 응답 유지 |
| 감사 로그 상세 | **서비스 명령 단위 직접 기록 보강** | 대상 ID와 before/after 또는 변경 건수를 남겨 M2 변경 추적성 확보 |
| 미리보기 범위 | **M2 서버 렌더 시뮬레이터** | M3 챗봇 위젯 미구현 상태가 M2 구현을 막지 않도록 분리 |
| 키워드/유사어 저장 | **트랜잭션 replace 방식** | 일괄 저장 실패 시 이전 데이터 유지 |
| 게시 버전 수정 | **직접 수정 금지, 복제 후 새 초안** | 게시 이력의 의미와 롤백 가능성 보존 |
| 기존 게시 버전 처리 | **새 게시 성공 시 기존 PUBLISHED는 ARCHIVED** | 활성 게시 버전 단일성을 보장 |

M2 구현은 아직 시작하지 않는다. 위 결정은 `1.기획/M2_갭점검메모_2026-05-08.md`와 M2 상세 작업지시서의 기본값으로만 사용한다.

## 8. M3 챗봇 런타임 설계 결정 (2026-05-08)

| 항목 | 선택 | 사유 |
|------|------|------|
| 비로그인 사용자 식별 | **HttpOnly `anonymous_id` 쿠키(UUID, 1년) + 서버 세션** | IP 기반 식별보다 개인정보 위험을 낮추면서 이력 연결 가능 |
| 대화 상태 저장소 | **`chat_session` DB 테이블** | 만료, 복구, 운영 추적, 단일 노드 운영에 적합 |
| fallback 정책 | **M3는 키워드 결과 카드 + M4 검색 stub** | 검색 품질 고도화는 M4로 넘기고 M3는 실패 기록과 인터페이스 확보 |
| 추천 질문 | **운영자 고정값 우선** | 초기 데이터 부족을 운영자 큐레이션으로 보완 |
| 대화 이력 보존 | **90일** | 품질 분석과 개인정보 최소 보존의 균형 |
| 만족도 | **UP/DOWN + 선택 코멘트** | 낮은 비용으로 개선 단서 확보 |
| 조건식 실행 | **M3 제외, 옵션 단순 분기만 지원** | 보안 검증과 테스트 난이도 축소 |
| 사용자 화면 채널 | **전용 페이지 `/chat` 우선** | 삽입형 위젯의 CSP/CORS 정책은 후속 설계로 분리 |
| 실패 상세 사전 | **`chat_failure.detail` 표준 키 사전 사용** | 실패 큐, 운영 지표, M4/M6 후속 분석에서 동일 JSON 키 사용 |

## 9. 공통 보안/인프라 결정 (2026-05-08)

| 항목 | 선택 | 적용 범위 |
|------|------|------|
| OPERATOR 시드 | **운영 기본 계정은 비활성 상태로 생성하고 `must_change_password=true`로 시딩** | M2 인증 보완. `users.must_change_password BOOLEAN NOT NULL DEFAULT false`는 Flyway V3.1에서 분리 추가. 정식 사용자 관리 UI는 M6에서 확장 |
| 쿠키 보안 속성 | **`SameSite=Lax`, `Secure=true`, `HttpOnly=true`** | `anonymous_id`와 세션성 식별 쿠키 기본값. JS 접근이 필요한 CSRF 토큰 쿠키는 `HttpOnly=false` 예외, `Secure=true`와 `SameSite=Lax`는 동일 적용 |
| 프록시 헤더 | **`server.forward-headers-strategy=framework`** | nginx HTTPS 종단 전제. `ForwardedHeadersBootCheck`는 `prod` 프로파일에서만 부팅 경고 로그 출력 |
| 매칭 캐시 TTL | **기본값 300초** | M3 키워드/유사어 매칭 캐시. 게시/상태변경/키워드 저장 성공 시 무효화 훅을 우선하고, 훅 부재 시 짧은 TTL로 정합성 보완 |

위 4건은 1~3번 문서의 단일 기준값이다. M2 구현은 아직 시작하지 않고, 현재 단계에서는 문서 동기화만 수행한다.

### 9.1 Flyway 분리 기준

| 파일 | 범위 | 비고 |
|---|---|---|
| `V3__scenario_baseline.sql` | M2 시나리오/버전/노드/옵션/키워드/유사어 테이블 | 기존 인증 테이블 변경을 포함하지 않는다. |
| `V3_1__auth_must_change_password.sql` | `users.must_change_password BOOLEAN NOT NULL DEFAULT false` 추가 | OPERATOR 시더는 비활성 계정과 `must_change_password=true` 기본값을 사용한다. |
