## 2. 명시적으로 채택하지 않은 것

| 미채택 | 사유 |
|--------|------|
| **JPA** | MyBatis와 혼용 시 트랜잭션·캐시 경계 복잡. 단순 CRUD도 MyBatis로 통일 |
| **Gradle** | 공공기관 인수·인계 시 Maven이 무난 |
| **Redis** | 단일 노드 가정. 세션·캐시는 JDBC/Caffeine로 충분 |
| **Elasticsearch** | 초기 데이터량 가정 시 PostgreSQL FTS로 충분. M4 이후 필요 시 도입 |
| **Spring Security** | 2026-05-12 §9.3 결정에 따라 미채택. 인터셉터+세션 VO로 대체 |
| **Docker(운영)** | 온프레미스 정책상 컨테이너 불가한 곳 다수. 개발환경 PostgreSQL만 Docker Compose 제공 |
| **클라우드 KMS/Vault** | 온프레미스 가정. 시크릿은 OS 환경변수 + 권한 분리된 properties 외부 파일 |

## 3. 패키지·디렉토리 규약

> 2026-05-13 정정: 본 절의 CleverChat 초기 `domain/common` 기반 Spring Boot 스타일 구조는 구현 출발점과 현행 분석 대상으로만 남긴다. 최종 목표 구조가 아니며, 코드 작성 형태, 폴더 구조, 패키지 명명, Controller/Service/Mapper/XML 구성, SQL ID 규칙, 화면 파일명, 화면 액션명, 관리자 UI 디자인/레이아웃/CSS/템플릿 구성의 최종 기준은 §11 "8소스 우선 정렬 원칙"이다.

- 그룹/모듈 groupId: `kr.co.cleverchat` 유지
- 목표 Java 패키지 축: `kr.core`, `kr.admmgr`, `kr.admmgr.<기능별>`, `com`
  - `kr.core`: 공통 코어, 애플리케이션/웹 설정, 세션/공통 부트스트랩 등 8소스의 코어 축을 따른다.
  - `kr.admmgr`: 관리자 업무 root다.
  - `kr.admmgr.<기능별>`: 관리자 업무 기능별 패키지다. `scenario`, `member`, `security`, `chat`, `search`처럼 업무 단위로 평탄화한다.
  - `com`: 공통/외부 유틸, 핸들러, 로그, 기반 유틸 계열을 둔다.
  - Maven `pom.xml`의 `groupId`는 `kr.co.cleverchat`로 유지한다.
  - 8소스 정렬 원칙에 따라 Java package root는 위 목표 축으로 단계 정렬한다.
  - `kr.co.cleverchat` 현행 Java package group은 전환 완료 전까지 동일 모듈 안에서 임시 공존할 수 있다.
- 현행 모듈 구조 (도메인 중심, 최종 목표 아님):
  ```
  kr.co.cleverchat
  ├── CleverChatApplication
  ├── config/        (Security, Web, MyBatis, Async 등 인프라 설정)
  ├── common/        (예외, 응답 포맷, 유틸, 감사 AOP)
  ├── web/           (사이트 공통 페이지 — 홈/에러/안내)
  └── domain/
      ├── auth/      (관리자 인증·권한)
      ├── admin/     (관리자 화면 공통)
      ├── scenario/  (시나리오·노드 관리)
      ├── chatbot/   (사용자 챗봇 런타임)
      ├── search/    (검색)
      ├── crawl/     (크롤링·파싱)
      └── ops/       (공지·통계·감사 조회)
  ```
- 모듈 내 표준 하위 패키지: `controller / service / mapper / dto / model`
- MyBatis 매퍼 XML: `src/main/resources/mapper/<domain>/*.xml`
- Flyway: `src/main/resources/db/migration/V{n}__{name}.sql`

## 4. 환경 분리

| 프로파일 | 용도 | DB | 로그 | HTTPS |
|----------|------|----|----|------|
| `dev` | 로컬 개발 | Docker Compose PostgreSQL | 콘솔, DEBUG | 미사용 |
| `stage` | 검증 | 물리 PostgreSQL (검증 DB) | 파일+JSON, INFO | nginx 종단 |
| `prod` | 운영 | 물리 PostgreSQL (운영 DB) | 파일+JSON, WARN | nginx 종단 |

- 시크릿(`spring.datasource.password` 등)은 절대 `application-*.yml`에 평문 저장하지 않는다.
- 운영은 `${DB_PASSWORD}` 등 OS 환경변수 또는 `--spring.config.additional-location`으로 외부 파일 주입.

## 5. 추후 재검토 트리거

- 동시 사용자 100 이상, 또는 다중 노드 도입 → **Redis 세션·캐시**, **Quartz JDBC 스케줄러**, **Rate limit 분산 저장소(Redis 토큰버킷 또는 PostgreSQL advisory window)**
- 검색 결과 품질 한계, 또는 백데이터 100만건 이상 → **Elasticsearch** 도입
- AI 답변 추천 요구 확정 → **벡터 DB (pgvector)** 검토 후 RAG 구조
- 멀티테넌시 요구 → 스키마 분리 vs 컬럼 분리 재설계

## 7. M2 구현 전 기본값 결정 (2026-05-08)

| 항목 | 선택 | 사유 |
|------|------|------|
| OPERATOR 계정 | **운영 기본 계정 비활성 시딩 + 최초 로그인 비밀번호 강제 변경** | 운영 진입 계정을 제공하되 기본 비밀번호 사용과 즉시 권한 행사를 차단 |

| 관리자 REST 오류 | **`/admin/api/**`는 JSON 401/403 반환** | AJAX 호출에 HTML 로그인 페이지가 섞이지 않도록 공통 응답 유지 |
| 감사 로그 상세 | **서비스 명령 단위 직접 기록 보강** | 대상 ID와 before/after 또는 변경 건수를 남겨 M2 변경 추적성 확보 |
| 미리보기 범위 | **M2 서버 렌더 시뮬레이터** | M3 챗봇 위젯 미구현 상태가 M2 구현을 막지 않도록 분리 |
| 키워드/유사어 저장 | **트랜잭션 replace 방식** | 일괄 저장 실패 시 이전 데이터 유지 |
| 게시 버전 수정 | **직접 수정 금지, 복제 후 새 초안** | 게시 이력의 의미와 롤백 가능성 보존 |
| 기존 게시 버전 처리 | **새 게시 성공 시 기존 PUBLISHED는 ARCHIVED** | 활성 게시 버전 단일성을 보장 |

## 8. M3 챗봇 런타임 설계 결정 (2026-05-08)

| 항목 | 선택 | 사유 |
|------|------|------|
| 비로그인 사용자 식별 | **HttpOnly `anonymous_id` 쿠키(UUID, 1년) + 서버 세션** | IP 기반 식별보다 개인정보 위험을 낮추면서 이력 연결 가능 |
| 대화 상태 저장소 | **`chat_session` DB 테이블** | 만료, 복구, 운영 추적, 단일 노드 운영에 적합 |
| fallback 정책 | **M3는 키워드 결과 카드 + M4 검색 stub** | 검색 품질 고도화는 M4로 넘기고 M3는 실패 기록과 인터페이스 확보 |
| 추천 질문 | **운영자 고정값 우선** | 초기 데이터 부족을 운영자 큐레이션으로 보완 |
| 대화 이력 보존 | **90일** | 품질 분석과 개인정보 최소 보존의 균형 |
| 만족도 | **UP/DOWN + 선택 코멘트** | 낮은 비용으로 개선 단서 확보 |
| 조건식 실행 | **M3 제외, 옵션 단순 분기만 지원** | 보안 검증과 테스트 난이도 축소 |
| 사용자 화면 채널 | **전용 페이지 `/chat` 우선** | 삽입형 위젯의 CSP/CORS 정책은 후속 설계로 분리 |
| 실패 상세 사전 | **`chat_failure.detail` 표준 키 사전 사용** | 실패 큐, 운영 지표, M4/M6 후속 분석에서 동일 JSON 키 사용 |
| 실패 검토 코멘트 | **`chat_failure.review_comment`는 V4 baseline에 포함** | 현재 실제 V4 SQL과 mapper는 미작성 상태이며, ERD/API/작업지시서는 `review_comment`를 포함한다. 운영 데이터 누적 전 baseline 단계이므로 V4_1 분리 없이 V4 작성 시 SQL/model/mapper에 함께 반영한다. |

## 9. 공통 보안/인프라 결정 (2026-05-08)

| 항목 | 선택 | 적용 범위 |
|------|------|------|
| OPERATOR 시드 | **운영 기본 계정은 비활성 상태로 생성하고 `must_change_password=true`로 시딩** | M2 인증 보완. `users.must_change_password BOOLEAN NOT NULL DEFAULT false`는 Flyway V3.1에서 분리 추가. 정식 사용자 관리 UI는 M6에서 확장 |
| 쿠키 보안 속성 | **`SameSite=Lax`, `Secure=true`, `HttpOnly=true`** | `anonymous_id`와 세션성 식별 쿠키 기본값. JS 접근이 필요한 CSRF 토큰 쿠키는 `HttpOnly=false` 예외, `Secure=true`와 `SameSite=Lax`는 동일 적용 |
| 프록시 헤더 | **`server.forward-headers-strategy=framework`** | nginx HTTPS 종단 전제. `ForwardedHeadersBootCheck`는 `prod` 프로파일에서만 부팅 경고 로그 출력 |
| 매칭 캐시 TTL | **기본값 300초** | M3 키워드/유사어 매칭 캐시. 키워드 replace 저장 성공 시 `ScenarioMatchingCacheInvalidator.onScenarioChanged(scenarioId)` 적용 완료. 게시/상태변경 성공 훅은 후속 구현에서 같은 무효화 규약을 따른다. |

### 9.4 관리자 native form CSRF 적용 정책 (2026-05-22)

- 관리자 인증 후 상태 변경 native form은 `admmgr/common/_csrfHidden :: csrfHidden` fragment를 포함한다. 적용 범위는 `templates/admin/**`, `templates/admmgr/**`의 `method="post"` form과 `ADM.Form.submit` 기반 제출 화면이다.
- `/logout`는 로그인 세션을 보유한 상태 변경 요청으로 보아 자체 CSRF 검증 대상에 포함한다. 로그아웃 form은 hidden fragment를 제출하고 `CsrfInterceptor` 적용 경로에 `/logout`를 포함한다.
- `/login` POST는 로그인 전 세션/관리자 세션이 없는 인증 진입점이므로 `_csrfHidden` 적용 대상에서 제외한다. 로그인 CSRF 보호는 별도 정책으로 확정하기 전까지 계정 잠금, 감사 로그, SameSite 쿠키 기준으로 보완한다.
- 신규 관리자 화면 추가 시 `method="post"` form과 `ADM.Form.submit` 호출은 hidden fragment 또는 CSRF 헤더 제출 여부를 PR 체크리스트에서 확인한다.

## 11. 8소스 우선 정렬 원칙 (2026-05-13)

### 11.1 베이스 소스 격상

`8.소스/OverseasNPP_20260511`은 참고자료가 아니라 CleverChat 개발의 원본 베이스 소스다. 앞으로 CleverChat의 코드 작성 형태, 폴더 구조, 패키지 명명, Controller/Service/Mapper/XML 구성, SQL ID 규칙, 화면 파일명, 화면 액션명, 관리자 UI 디자인/레이아웃/CSS/템플릿 구성은 8소스를 우선 기준으로 맞춘다.

CleverChat 현재 `domain/common` 기반 Spring Boot 스타일 구조는 기준이 아니라 조정 대상이다. 최종 목표 구조는 `kr.core`(공통 코어), `kr.admmgr`(관리자 업무 root), `kr.admmgr.<기능별>`(업무 패키지), `com`(공통/외부 유틸) 축이며, 기능별 업무 패키지 중심 구조로 단계적으로 정렬한다. 다만 Spring Boot 3, Thymeleaf, REST JSON 유지처럼 기술적으로 불가피하거나 이미 결정된 차이는 §11.3 예외 표에 한정한다.
