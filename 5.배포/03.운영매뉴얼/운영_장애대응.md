## 일상 점검

| 순서 | 확인 대상 | 정상 판단 |
|---:|---|---|
| 1 | 서비스 프로세스, health, DB 연결 | 해당 버전 프로세스가 하나씩 정상 기동, `/actuator/health` 200/UP |
| 2 | 로그인/관리자 접근 | 현재 LOCAL/GATEWAY 모드에 맞는 로그인, 역할·IP 허용 정상 |
| 3 | 상담 검색·이전 | 관련 메뉴/문서, 선택한 세부 노드, 실제 직전 화면 복원 |
| 4 | 수집 큐·최근 실패·예약 | PENDING/RUNNING 장기 적체 없음, 실패 이유·재시도 여부 확인 |
| 5 | JSON/로그/DB 디스크 | 서비스 계정 쓰기 가능, 예상 경로, 충분한 여유 공간 |
| 6 | 백업·유지보수 | 백업 생성/해시/외부 보관, 최근 정리 작업 결과, 복구 리허설 기록 |

개발 DB의 읽기 전용 점검 예시(다른 환경에서는 접속 대상과 스키마를 교체):

```sql
SELECT version, script, success
FROM cleverchat_dev.flyway_schema_history
ORDER BY installed_rank DESC LIMIT 5;

SELECT status, count(*)
FROM cleverchat_dev.tb_crawl_job GROUP BY status ORDER BY status;

SELECT crawl_job_no, target_no, status, attempt_count,
       requested_at, started_at, finished_at, message
FROM cleverchat_dev.tb_crawl_job
WHERE status IN ('PENDING','RUNNING','FAILED')
ORDER BY requested_at DESC LIMIT 30;

SELECT task_key, run_date, started_at, finished_at, message
FROM cleverchat_dev.tb_maintenance_run
ORDER BY run_date DESC LIMIT 7;
```

로그/조회 결과에는 URL·사용자 정보가 포함될 수 있으므로 장애 보고서에는 필요한 식별자와 마스킹한 내용만 남긴다.

## 크롤링 실행과 JSON 확인

1. 시스템 설정에서 수집 작업 실행을 켠다. 동적 게시판은 브라우저 수집과 Chromium 환경도 확인한다.
2. `/admin/crawl-targets`에서 대상 URL, 사용 여부, 수집 방식, 예약, 제한을 확인한다.
3. JSON을 보관하려면 시스템 기본 폴더 또는 대상의 별도 폴더를 **앱 서버 절대 경로**로 지정하고 대상의 JSON 저장을 켠다. 사용자 PC 다운로드 폴더를 의미하지 않는다.
4. 수동 실행 후 작업 큐를 확인한다. 버튼 응답은 작업 접수이며 전체 수집 완료를 의미하지 않는다.
5. 대상 상세 실행 이력에서 페이지별 수집 상태, 실패 코드, 파일 저장 상태/경로를 확인한다. 문서 수집과 JSON 저장 실패는 따로 판정한다.
6. 파일 존재와 UTF-8 JSON 내용을 확인한다. 본문이 같아 DB 중복으로 처리된 페이지도 파일은 새로 생성한다.

파일 규칙: `<저장 루트>/target-<대상 번호>/<수집일>/<UUID>.json`. 파일 스키마는 아래와 같다. 값은 형식 설명이며 실제 수집 데이터가 아니다.

| 필드 | 의미 |
|---|---|
| `schemaVersion` | 현재 1 |
| `crawledAt` | 수집 시각 문자열 |
| `targetId`, `targetLabel` | 대상 번호/표시명 |
| `documentId` | DB 문서 식별자 |
| `url`, `title`, `content` | 수집 URL·제목·본문 |
| `contentHash` | 수집 문서 내용 해시 |
| `httpStatus` | HTTP 상태 |

파일 저장은 임시 파일 작성 후 이동 방식이다. `.tmp`는 완료 파일이 아니다. `tb_crawl_export_file.content_sha256`는 **저장 파일 전체의 해시**이며 문서 본문 `contentHash`와 동일하다고 가정하지 않는다. 경로 변경은 기존 파일을 옮기지 않으며 자동 정리는 생성 당시 경로 기준이다.

## 주기 작업·보관 기준

| 작업 | 주기/기본값 | 변경 위치와 주의점 |
|---|---|---|
| 예약 수집 검사 | fixed delay 60초 | 대상 예약 시각을 검사해 큐에 추가. 정확히 매 정각 완료 보장 아님 |
| 작업 큐 소비 | 기본 fixed delay 5초 | worker poll 환경 설정, 실행 여부는 런타임 설정 |
| 대화 세션 만료 | 10분마다 | 만료시각 지난 세션 상태 변경 |
| 대화 데이터 삭제 | 매일 03:30, 생성 후 90일 | `ChatRuntimeMaintenanceService`의 고정값. 500건 단위 반복 삭제. JVM 시간대 기준 |
| 실패·중복 수집 문서 정리 | 매일 기본 03:45, 90일 | 시스템 설정, 성공 문서는 보관. 한국 시간 기준 |
| 크롤링 실행 로그 정리 | 같은 유지보수 작업, 365일 | 시스템 설정 |
| JSON 파일 정리 | 기본 OFF, 90일 | 켜면 등록 파일 중 만료·경로/해시 검증 통과 파일 대상 |
| 검색 로그 정리 | 관리 화면/API의 정리 작업 | 기본 보관 90일 설정은 자동 스케줄 추가를 의미하지 않음 |
| HTTP 세션 정리 | Spring Session JDBC | 상담 테이블과 별개 |
| DB 백업 | 앱 내 스케줄 없음 | OS 스케줄러/운영 도구로 별도 등록 |

수집/JSON 유지보수는 매분 현재 시각을 검사하고 DB에서 하루 실행을 점유한다. 해당 분에 서버가 꺼져 있으면 재시작 직후 누락 작업을 소급 실행하지 않는다. `tb_maintenance_run`에서 결과를 확인한다. 조회 범위인 `CHAT_HISTORY_DAYS`와 실제 대화 삭제 90일 정책을 혼동하지 않는다.

## 로그 위치

dev는 기본 콘솔 출력이다. 실행 도구가 별도로 리다이렉트한 로그와 애플리케이션 표준 파일 로그를 구분한다. stage/prod는 `LOG_DIR`(기본 `/var/log/cleverchat`)를 사용한다.

| 파일 | 용도 | logback 기본 보관 |
|---|---|---:|
| `app.log` | 애플리케이션 일반 로그 | 90일 |
| `api.log` | API 이벤트 | 90일 |
| `security.log` | 인증·보안 이벤트 | 365일 |
| `error.log` | 오류 | 180일 |
| `slow-query.log` | 느린 SQL | 90일 |
| Tomcat access log | HTTP 접근 | `server.tomcat.accesslog` 별도 설정 확인 |

각 logback appender는 파일당 100MB, 총 20GB 상한이 있어 용량 때문에 기간보다 먼저 정리될 수 있다. 실제 정책은 `logback-spring.xml`이 기준이며 stage yml의 rolling 30일 설명만 보고 판단하지 않는다. Tomcat access log 경로는 현재 `/var/log/cleverchat`에 별도 설정되어 있다.

| 서버가 안 뜸 | Java 버전, 포트 점유, DB 접속/스키마, Flyway 실패, stage/prod 암호화 키 | 최초 원인 로그부터 해결. 이력 삭제로 우회하지 않음 |

| 설정을 바꿔도 값이 그대로 | DB에 저장된 runtime 값, 다른 탭의 낙관적 버전 충돌, 환경값 변경 후 재시작 여부 | 시스템 설정 재조회/저장. 환경변수보다 DB 저장값 우선 |
| 작업이 PENDING에 머묾 | worker 실행 여부, 실행 슬롯, 이미 진행 중인 작업 | 큐/로그를 함께 확인하고 다음 poll 대기. 작업 행을 바로 삭제하지 않음 |
| RUNNING 장기 잔류 | 외부 사이트 응답, Chromium 프로세스, 기본 180분 복구 기준/최대 시도 | 실제 실행 중인지 확인 후 서비스 복구. 시간 초과/재시도 결과 확인 |
| HTML은 되는데 게시판 실패 | 브라우저 ON, Chromium 바이너리·OS 라이브러리·서비스 계정 권한, 프록시/CA | 같은 실행 계정으로 검수. selector는 대상 사이트 HTML에 맞춰 점검 |
| 링크/본문 누락 | robots/URL 정책, 최대 발견·페이지·상세 제한, 사이트 구조 변경 | 실패 코드/coverage/제한 도달 여부 확인. robots/보안 정책을 일괄 끄지 않음 |
| DB에는 있는데 JSON 없음 | 대상 저장 스위치, 유효 저장 루트, `export_status`/오류, 디스크/권한 | 실행 이력의 파일 오류를 해결하고 재실행. JSON 실패를 DB 미수집으로 단정하지 않음 |
| JSON 정리 안 됨 | 기본 OFF, 레지스트리 미등록 과거 파일, 생성 후 기간, 경로·해시 변경 | 등록된 파일만 정리되는 설계. 무관한 파일을 강제로 등록하지 않음 |
| 검색 내용이 안 맞음 | 활성 발행 버전/노드, 제목/본문/토큰, 점수/표시 설정 | 관련 없는 상위 메뉴를 강제로 넣지 않음. 전기요금·납부·할인 등 다른 의도도 함께 확인 |
| 이전이 예상 경로와 다름 | 선택 출처 `sourceMessageId`, BOT payload의 부모, 구형 메시지/발행 버전 | 실제 클릭한 말풍선과 세션을 재현. UI·DTO·서버를 함께 확인 |
| vLLM 실패/기존 답변만 나옴 | AI ON, 저장한 `/v1` URL/모델, 키, `/models` 테스트, 응답 지연 | 실제 생성 호출도 검수. timeout/오류 시 검색 근거 답변으로 돌아가는 것이 정상 fallback |
| 연계 로그인 실패/401 | 공유 시크릿, 사번/서비스별 역할, 차단 계정, 헤더 전달 | Gateway 경유 실제 요청 확인. 로컬 비밀번호로 연계 인증을 우회하지 않음 |
| 과거 대화 복호화 오류 | key ID와 현재/이전 키 구성 | 백업과 맞는 키 복원. 새 키로 임의 교체하거나 암호문을 덮어쓰지 않음 |

## 검색·이전 동작 기준

검색 결과는 관련 **세부 노드**를 선택하면 그 노드로 들어간다. `scenarioNodeNo`를 루트 시나리오 번호로 바꾸면 관계없는 메뉴로 진입할 수 있다. 현재 선택 API는 선택이 발생한 BOT 말풍선의 `sourceMessageId`를 전달한다.

공통 버튼 문구는 `이전`이다. 서버의 `canGoBack`에 따라 표시하며 실제 방문한 부모 메시지를 복원한다. 문서 → 검색 목록 → 검색 직전 시나리오 순으로 돌아가야 한다. 시나리오에 등록된 `상위 메뉴/처음으로/이전` 선택지는 UI에서 걸러 중복을 피한다. `안내 종료`와 종료 후 복귀 정책은 별도로 검수하고, 모든 종료 상태에서 이전을 무조건 숨긴다고 가정하지 않는다.

## 백업과 복구

기존 [백업 스크립트와 실행법](../../3.개발/cleverchat/deploy/backup/README.md)을 사용한다. PGHOST/PGPORT/PGDATABASE/PGUSER/인증정보와 백업 경로를 별도로 주입하며, custom-format dump(`pg_dump -Fc --no-owner --no-acl`)와 SHA-256을 생성한다. 스크립트 기본 보관은 14일(최소 7일)이며 OS 예약·외부 저장소·암호화·알림은 추가 운영 설정이다.

1. DB 백업 해시와 `pg_restore --list`로 파일을 확인한다. 읽기 목록만 성공했다고 복구 검증 완료로 처리하지 않는다.
2. **운영과 분리된 빈 복구 DB**에 복원한다. 자동 수집/알림/JSON 정리와 경로·연계 주소를 먼저 검토한 다음 복구 앱을 실행한다.
3. 암호화 키를 맞추고 Flyway, 시나리오/문서 건수, 로그인, 검색/대화 이력/피드백을 확인한다.
4. 별도 백업한 JSON 파일과 경로를 확인한다. DB dump에는 JSON 원본 파일이나 OS 계정·비밀값이 들어 있지 않다.
5. [복구 검수표](../05.백업복구절차서/복구리허설_체크리스트.md)에 실제 복구 시간과 누락 여부를 기록한다. WAL/PITR는 [기존 절차](../05.백업복구절차서/PITR_복구절차.md)를 참조하되 서버에 WAL 보관이 실제 구성되어 있는지 먼저 확인한다.

## Gateway 장애 시 독립 모드 복구

기존 LOCAL ADMIN 계정이 유지되고 정상 사용 가능한지 전환 전에 확인한다. Gateway 접근 장애로 관리자 화면에 들어갈 수 없을 때 DB 담당자가 대상 스키마와 작업 권한을 확인하고 아래처럼 모드와 버전을 함께 바꾼다. 아래는 수동 복구 절차이며 평소 설정 변경은 화면을 사용한다.

```sql
UPDATE cleverchat_dev.tb_system_settings
SET operation_mode = 'LOCAL', version = version + 1,
    auth_version = auth_version + 1,
    updated_by = 'operator-recovery', updated_at = now()
WHERE id = 1;
```

대상 스키마를 실제 환경에 맞추고 영향 행 1건을 확인한다. 이후 `/login`에서 정상 로컬 인증, 세션 무효화, 관리자 IP 접근을 검수한다. 이 조치는 사용자 생성·비밀번호 초기화·잠금 해제나 인증 우회가 아니다. 수행 기록을 남기고 Gateway 복구 후 재연계한다.
