# M2 배포 메모

> 작성일: 2026-05-08

## 1. 배포 단위

- 애플리케이션 JAR
- Flyway `V3__scenario_baseline.sql`
- Flyway `V3_1__auth_must_change_password.sql`
- Thymeleaf 관리자 시나리오 화면

## 2. 배포 전

- stage DB 백업
- `mvn test` 수행
- stage 프로파일 기동 및 Flyway 적용 확인
- 관리자 계정과 OPERATOR 계정 권한 확인
- V3는 시나리오 baseline만 포함하고, V3.1에서 `users.must_change_password`만 추가되는지 확인
- OPERATOR 시드 기본값이 `enabled=false`, `must_change_password=true`인지 확인
- 쿠키 속성 기준(`SameSite=Lax`, `Secure=true`, `HttpOnly=true`, CSRF 토큰 쿠키 `HttpOnly=false` 예외) 확인
- nginx `X-Forwarded-*` 헤더와 `server.forward-headers-strategy=framework` 조합 확인
- 매칭 캐시 TTL 기본값 300초 설정 확인

## 3. 배포 후

- `/actuator/health` 확인
- `/login` 로그인 확인
- `/admin/scenarios` 접근 확인
- 시나리오 생성/게시 테스트 데이터 1건 확인 후 삭제 또는 비활성화
- `audit_log` 기록 확인
- `/admin/password-change` 화면 접근과 비밀번호 변경 후 `must_change_password=false` 전환 확인
- prod 프로파일에서만 프록시 헤더 부팅 경고 로그가 출력되는지 확인

## 4. 롤백

- 코드 롤백은 이전 JAR로 재기동한다.
- DB 롤백은 자동 down migration을 사용하지 않고, 배포 전 백업 복구를 기본으로 한다.
- V3 적용 후 운영 데이터가 생성된 경우 DBA/운영자 승인 없이 테이블 삭제를 수행하지 않는다.
- V3.1 적용 직후 운영 계정 변경 데이터가 없으면 `users.must_change_password` 컬럼 단독 롤백 가능성을 DBA와 검토할 수 있다. 운영 데이터 생성 후에는 백업 복구 기준을 따른다.
